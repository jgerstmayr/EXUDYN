Building and running

Three pages, in the order a new developer needs them:

GETTING_STARTED.md

from nothing: clone, environment, setupLocalWorkspace.py, first build, first test run

BUILD.md

the build itself, per platform, and what to do when it does not work

GIT.md

branches, commit messages, pull, push, merge, and what a contribution provides

Editors. The everyday work happens in VS Code - the Python package, the definition files, the documentation, and Claude Code. Visual Studio 2022 is the debugger: stepping from a Python script into a C++ item’s ComputeODE2LHS with one debugger is the project’s most valuable development capability and is protected by design. tools/setupLocalWorkspace.py prepares both.

The driver: one command, exudev - exudev --help, and exudev -n <command> to see what a command would run without running it. Its commands are in tools/exudev/README.md.

Entry points worth knowing:

  • src/Pymodules/PybindModule.cpp — module creation.

  • src/Main/MainObjectFactory.h/.cpp — item creation behind mbs.AddNode(...); dispatch is on the objectType string from the Python dict, through a runtime class-factory registry.

Invariants

These are differentiators, not technical debt. Every restructuring step preserves them (plan §7):

  • Mixed Python/native debugging in VS2022 - the capability, not which editor is primary; the everyday work happens in VS Code.

  • The setuptools-based fast build.

  • No heavy C++ dependencies; vendored headers.

  • The hard C++/Python split with dict-based validated interfaces.

  • Runtime dependencies stay at numpy only. Development-only tools are unconstrained.
