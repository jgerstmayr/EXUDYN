# Exudyn coding style and conventions

> **Source of truth.** This file is a Markdown transcription of
> `docs/theDoc/introduction.tex`, sections *Code style and conventions*, *Notation conventions*
> and *No-abbreviations-rule*, plus the abbreviation table from `docs/theDoc/abbreviations.tex`.
> Those LaTeX files still ship in `theDoc.pdf`. If you change a rule, change it in **both** places
> until revision2026 step R7.1 makes RST/Sphinx primary and this duplication goes away.

## 1. General rules

- Write **simple** code — no complicated structures, no uncommon constructs.
- Write **readable** code: variables and functions named for their content or functionality.
  Avoid abbreviations (§4).
- Put a **header in every file** (§7).
- Put a comment on every global function, member function, data member and template parameter.
- **Always use curly brackets**, including for single statements:
  `if (i < n) { i += 1; }`
- **4-space tabs, expanded to spaces.**
  VS: *Extras → Options → C/C++ → Tabstopps*: tab size 4, **keep spaces = yes**.
- Use C++11 where appropriate, but not exhaustively - prefer readability for engineering programmers.
- Use C++14 - C++20, if very helpful and reducing the overall code size, or to avoid larger workarounds and to enable future extensibility; switching to C++20 features shall be reported by Claude.
- Standards after C++20 should be used with care: we like to have multi-platform compatibility, mini computers (Raspberry) often have older setups, so we should not require too modern compilers.
- **One class, one file** — except for collectors of single implementation functions.
- Avoid large classes: more than 45 member functions or more than 30 data members is a warning;
  more than 60 member functions is a god class and should be split - except for some autogenerated containers or similar.
- Mark changed code with your name and the date.

Stated priorities, in order: developer-friendliness, error minimization, user-friendliness,
efficiency.

## 2. Notation conventions

The source states these with *"no exceptions"*.

| kind | case | examples |
|---|---|---|
| variables, class members, consts, defines | `lowerCamelCase` | `secondOrderSize`, `massMatrix`, `mThetaTheta` |
| functions, classes, structs | `UpperCamelCase` | `SecondOrderSize`, `EvaluateMassMatrix` |

Exception: algorithms that follow a formula may mirror the formula —
`f = M*q_tt + K*q`, `GBar`.

**Abbreviations inside CamelCase** — the one rule that trips people up:

- In **functions and classes**, an upper-case abbreviation continues **upper case**:
  `ODESystem`, `Point2DClass`, `ANCFCable2D`, `ANCFALE`, `ComputeODE1Equations`.
  ("Not always nice to read, but has become a standard and will be further used.")
- In **variables and class members**, it continues **lower case**:
  `nODE1variables`, `dim2Dspecial`, `ANCFsize`.
- At the *beginning* of a name: functions and classes may lead with the abbreviation
  (`ODEComputeCoords()`); variables must not — write `nODE` or `odeCoordinates`.

Further:

- **American English** throughout (`Visualization`, not `Visualisation`).
- Avoid consecutive capitalized words — avoid `ODEAE`.
- No underscore in names. **Exception: derivatives** (§3).
- Name exactly what the thing is: `numberOfItems`, not `size` or `l`.
- **Get/Set convention**: `Get` when data is retrieved from a class, `Set` when something is set.
  Use `const T& Get()` / `T& Get()` where direct access is needed. Same convention for pybind11.
  Examples: `Real* GetDataPointer()`, `Vector::SetAll(Real)`, `GetTransposed()`,
  `SetRotationalParameters(...)`, `SetColor(...)`.
- Use **`Real`**, not `double` or `float` — compatibility, and single/double precision under AVX.
- Use **`Index`** for sizes and indices, not `size_t` or `int`.
- **No magic numbers** — not even `3` for 3D or a rotation-parameter count. Define a
  `const Index` or `constexpr`.

## 3. Suffix conventions

| suffix | meaning |
|---|---|
| `_t`, `_tt` | first / second time derivative — `Position_t`, `Position_tt` |
| `_x`, `_xx`, `_y`, ... | spatial derivatives |
| `_q` | derivative with respect to coordinates (scalar quantity) |
| `_v` | derivative with respect to velocity coordinates |
| `[...]Init` | argument initializing a member — `valueInit` initializes `value` |

For components, elements and entries of vectors, arrays and matrices, use the word **`item`**
throughout.

## 4. The no-abbreviations rule

The code uses a **minimum set of abbreviations**. In general: do not abbreviate function, class or
variable names — `GetDataPointer()`, not `GetPtr()`. Short loop-local names (`cnt`, `i`, `j`, `k`,
`x`, `v`) are acceptable only where the meaning is unmistakable, in short (about 5-line) functions.

The permitted exceptions, in full: `ODE`, `ODE2`, `ODE1`, `AE` (as in `AEcoordinates`),
`C[...]` for *Computational* (`CNode` = ComputationalNode), `mbs`, `min`, `max`, `abs`, `rel`,
`trig`, `quad`, `RHS`, `LHS`, `EP`, `Rxyz`, `coeffs`, `pos`, `T66`.

Historical note: `ODE2` corresponds to `SOS2` / `EvalF2` in HOTINT, `ODE1` to `ES` / `EvalF`.

## 6. Item and dimensionality conventions

- An **item** is a node, object, marker, load or sensor — the five registered kinds.
- Each item has up to three halves: `CObject` (computational), `MainObject` (Python interface),
  `VObject` (visualization).
- **All indices start at 0**, in Python *and* in C++. Ranges are usually written `range(0,3)`,
  where 3 is the index after the last valid component.
- Quantities are **3D by default**. Planar items carry the suffix `2D`; 3D items carry no suffix.
  Rare exceptions exist where a Python name-space conflict would arise (e.g. `Beam3D`).
- Input and output of objects, markers and loads is usually 3D even when the node is 2D: a
  `NodePoint2D` has 2D `referenceCoordinates` but a 3D measured position, and a force applied
  through `MarkerNodePosition` + `LoadForceVector` is 3D. A local position in a 2D object is given
  as a 3D vector.

### References in comments

A comment that explains why code is the way it is cites the **issue** (`#2411`), not a step of the
revision plan: comments stay for years, issue numbers are stable and the issue names its plan step.
Plan steps are cited in issues and commit messages as "revision2026 step R4.10.3" (see
[`exudynRevisionInfo2026.md`](../revision/exudynRevisionInfo2026.md) §1).

## 7. File headers

**C++** — Doxygen-style block at the top of the file:

```cpp
/** ***********************************************************************************************
* @class        Vector
* @brief        A templated vector class ...
* @details      Details: ...
*
* @author       Gerstmayr Johannes
* @date         2018-04-30 (generated)
* @date         2024-01-15 (last modified)
* @pre          ...
* @copyright    This file is part of Exudyn. Exudyn is free software: ... see 'LICENSE.txt'
* @todo         ...
*
* *** Example code ***
* @code{.cpp}
* ...
* @endcode
************************************************************************************************ */
```

**Python** — banner comment:

```python
#+++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++
# This is an EXUDYN python utility library
#
# Details:  ...
#
# Author:   Johannes Gerstmayr
# Date:     2020-03-10 (created)
# Copyright:This file is part of Exudyn. Exudyn is free software: ... see 'LICENSE.txt'
#
#+++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++
```

## 8. Deprecated and in transition

These rules are documented in `introduction.tex` but are **not** consistently followed in the tree.
Do not enforce them retroactively, and do not introduce them into files that lack them.

| rule | status |
|---|---|
| Doxygen comment style (`//!`, `@todo`, `@test`, `@bug`) | **deprecated, and the toolchain is gone.** `docs/doxygen/` was removed 2026-09-10 — it broke on project size, the PDF path never worked, and graph generation had already been switched off. So nothing consumes these comments any more. New code need not adopt the style; existing blocks stay until a dedicated cleanup step. For the architectural overview doxygen was once expected to give, see [ARCHITECTURE.md](ARCHITECTURE.md). |
| "Add a complete unit test to every function" (LEST) | not obeyed. The LEST tests are gated on `PERFORM_UNIT_TESTS`, enabled only for Python 3.7, so they run nowhere. revision2026 step R5.3 wires them into the VS `Debug` configuration. |
| The `#**` doc-comment convention in `python/exudyn/` | **replaced 2026-09-15** (revision2026 step R4.6) by Google-style docstrings: summary, then `Args:`, `Returns:`, `Note:`, `Example:`, each section's text indented by four spaces. `author`, `date`, `status` and `public=False` go into `@docmeta(...)` (`exudyn/docmeta.py`), a MainSystem method is marked `@extends(exudyn.MainSystem)`. Every module in `python/exudyn` has an `__all__` listing its public names (top-level functions, classes and assigned names not starting with `_`, except `@docmeta(public=False)`); `python tools/checkAll.py --write` updates it after adding a function, and CI fails if it is incomplete (revision2026 step R4.22.3). The text is Markdown (revision2026 step R4.6.4): `code` in backquotes, `$...$` math, `[Key]` for a citation, `[text](#label)` for a reference (`[Section](#sec:...)`, an abbreviation as `[HT](#HT)`), `**bold**`, `*italics*`, UTF-8 characters instead of LaTeX accents; no LaTeX macros outside math. |

**The operative rule when editing an existing file: follow that file's local style.** A consistent
file beats a globally consistent repository during a migration.
