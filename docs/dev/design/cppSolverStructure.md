# The C++ solvers as they are (revision2026c step RG20.6)

A design note of an open step: the analysis of the present structure of the solvers of the C++ core - files, classes,
the step loop, Newton, step size control, output, the Python layer - as the basis of RG20.7 (TrapezoidalGGL and the
Runge-Kutta methods of exudyn.symbolics.advancedSolvers in C++). Sections 1 to 7 state what is there (RG20.6.1),
section 8 recommends the structure of the new solvers (RG20.6.2). It leaves the repository when the step closes
(WORKFLOW.md §8.4).

The system side that the solvers call is `CSystem` (`src/Main/CSystem.h`): `ComputeSystemODE2RHS`, the ODE1 right-hand

## 2. The classes

```
CSolverBase                                  data, it, conv, output, file, timer, newton, discontinuous, restart
 ├─ CSolverStatic                            load factor as time; Newton on the static residual
 ├─ CSolverImplicitSecondOrderTimeInt        generalized-alpha / Newmark / TrapezoidalIndex2
 │   └─ CSolverImplicitSecondOrderTimeIntUserFunction   each virtual function replaceable by a Python function
 └─ CSolverExplicitTimeInt                   RK tableaus, VelocityVerlet; Newton() is the explicit step
MainSolverBase  →  MainSolverStatic, MainSolverImplicitSecondOrder, MainSolverExplicit   (Python classes)
```

The data of a solver are the generated structures, public members of `CSolverBase`: `data` (`SolverLocalData`: sizes,
the system residual and Jacobian - dense or sparse `GeneralMatrix` -, the mass matrix, temporary vectors per thread,
`aAlgorithmic` of generalized-alpha), `it` (`SolverIterationData`: times, step sizes, counters, automatic step size
flags), `conv` (convergence flags and errors), `output`, `file`, `timer`. The state is not the solver's: it is
`CSystemData::cData`, with `currentState`, `startOfStepState`, `initialState` and `visualizationState`
(`CSystemState`: ODE2 coordinates and their two derivatives, ODE1 coordinates and velocities, AE and data
coordinates, time). A solver writes the current state, and the step loop copies it to the start of the step.

## 3. The step loop (CSolverBase::SolveSteps)

```
SolveSystem: InitializeSolver (pre-checks, data, output files, initial conditions: initial accelerations)
             SolveSteps; FinalizeSolver
SolveSteps:  FinishStep for the initial state (or the restart state)
             while not end time and not stopped:
                 startOfStepState = currentState
                 repeat until the step is accomplished or the step reduction failed:
                     InitializeStep              pre-step user function, UpdateCurrentTime (t += h)
                     DiscontinuousIteration      loop: Newton; FinalizeNewton; PostNewton (data coordinates)
                                                 - error > tolerance: back to the start state, again (or false
                                                   with a recommended smaller step)
                     failed: currentState = startOfStepState; ReduceStepSize (adaptiveStep, automaticStepSize)
                     done: FinishStep (post-step user function, solution and sensor files at the write periods,
                           visualization state, verbose output, real-time); after adaptiveStepRecoverySteps good
                           steps IncreaseStepSize
                 restart file at its write period
```

- **One step is one Newton solve** for the implicit solver: `Newton()` in the base class iterates
  `ComputeNewtonResidual` / `ComputeNewtonJacobian` / `ComputeNewtonUpdate` (virtual), with the modified Newton
  method (Jacobian kept over steps), the factorization of the linear solver, the divergence checks and the
  Jacobian update rules; the unknowns are the system coordinates `nSys = nODE2 + nODE1 + nAE` - for
  generalized-alpha the accelerations (ODE2), the ODE1 coordinates and the multipliers. A method with more unknowns
  per step (stages, mu of GGL) does not fit `nSys`.
- **The explicit solver overrides `Newton()`** with the whole explicit step (the stages, the final combination, the
  error estimate); the base class loop, the discontinuous iteration and the output are shared.
- **The static solver** uses the same loop with the load factor as time.

## 4. Step size control

- **Implicit (generalized-alpha)**: no error estimate. `adaptiveStep`: the step is reduced when Newton fails or the
  post-Newton step recommends a smaller step (`it.recommendedStepSize`, `adaptiveStepDecrease`), and increased after
  `adaptiveStepRecoverySteps` steps with few iterations (`adaptiveStepIncrease`); `ReduceStepSize` and
  `IncreaseStepSize` of the solver class.
- **Explicit**: `automaticStepSize` for the tableaus with an embedded method (ODE23, DOPRI5): inside `Newton()` the
  error of the embedded solution in the RMS norm with `absoluteTolerance` and `relativeTolerance` (positions,
  velocities, ODE1), the elementary controller h (1/e)^(1/q) with `stepSizeSafety`, `stepSizeMaxIncrease`,
  `minimumStepSize`; a rejected step repeated at once, an accepted one gives the next step size (#2109). The reduction
  by Newton/post-Newton failures is the shared path above.
- So there are two step size rules in C++, and a third in Python (the PI controller of `_ErrorStepSize`, RG20.8.1).
  The values a two-step error estimate needs - the stage velocities of the previous step - are not kept: the explicit
  solver keeps the stages of the current step only (`rk.stageDerivODE2`), the implicit solver none.

## 5. Output and restart

- `FinishStep` writes the solution file (`WriteCoordinatesToFile`, text or binary) and the sensors
  (`WriteSensorsToFile`, files and internal storage under the lock of each sensor) when the time passes a multiple of
  the write period - at the end of the step that passes it, not at the write time (RG20.4.2 open: interpolated output,
  done in Python, #3241). The visualization state is copied for the renderer; the pre- and post-step user functions
  are called in `InitializeStep` / `FinishStep`.
- The restart file (#2850): the state, the step index and step size, written at its period after a finished step;
  read and applied at the start of `SolveSteps`.
- `SolverOutputData` / the solver file: verbose output and statistics; the timer per phase (`CSolverTimer`).

## 6. The Python layer

- `MainSolverBase` exposes the C solver's phases to Python (`InitializeSolver`, `SolveSteps`, `Newton`,
  `ComputeNewtonResidual`, ... with a `MainSystem`), and its data structures (`it`, `conv`, `output`, `newton`,
  `timer`) as properties; the bindings are generated from `structureDefsSolvers.py`.
- `CSolverImplicitSecondOrderTimeIntUserFunction`: every virtual phase can be replaced by a Python function - used to
  write a solver in Python on the C++ loop (e.g. examples with a user Newton).
- `exudyn.solver.SolveDynamic` selects `MainSolverImplicitSecondOrder` or `MainSolverExplicit` by the solver type.
- The Python solvers of `exudyn.symbolics.solvers` and `.advancedSolvers` do not use the C++ loop: they have their own
  loop (`_StepSize`, `_ErrorStepSize`, `_Output`, `_PostNewton`), the same settings, and write through mbs
  (`WriteCoordinatesToFile`, `WriteSensorsToFile` of the Main solvers, #3241).

## 7. Observations for RG20.7 (facts, not yet recommendations)

- The step loop with rejection, the discontinuous iteration and the output are in the base class and can carry a new
  solver; the per-step Newton is generic as long as the unknowns are `nSys` and the Jacobian one system matrix.
- TrapezoidalGGL needs `nODE2 + nODE1 + 2 nAE` unknowns (mu); the Runge-Kutta methods `s (nODE2 + nODE1) + k nAE`.
  `SolverLocalData` sizes its vectors and matrices by `nSys`, and `ComputeNewtonJacobian` assembles the system
  Jacobian of one state - a stage method needs the Jacobian at each stage, or one shared (simplified Newton).
- An error estimate from two steps needs the stage velocities (and accelerations) of the previous accepted step kept
  in the solver, and the first step a one-step estimate.
- The two existing step size rules (explicit error control, implicit adaptive step) and the Python PI controller are
  separate code; RG20.8.2 (#3245) is the common controller.
- The output at the write times needs the state within the step (Hermite interpolation of q, v), which
  `FinishStep` does not have (RG20.4.2).

## 8. Recommendations for the C++ solvers (RG20.6.2)

### 8.1 What goes into C++ (maintainer 2026-11-05)

- The methods: **TrapezoidalGGL**, **LobattoIIIA4** (the constraints at the end of the step), **LobattoIIIC4-GGL**
  and **Radau3** - the forms of `exudyn.symbolics.advancedSolvers`; the other variants measured in RG20.2
  (advancedSolvers.md section 3.2: constraints at all stages, index 3 at the stages alone, one shared multiplier)
  are not implemented. The automatic step size for TrapezoidalGGL and one Lobatto method.
- No Python interface of their phases: the MainSolver classes (`MainSolverImplicitSecondOrder`, ... with
  `ComputeNewtonResidual` and the rest) and the user-function solver are not made for them; the pre- and post-step
  user functions are the access of a script; special studies use the solvers of exudyn.symbolics.

### 8.2 One class for the four methods

The four are one algorithm: a stiffly accurate implicit Runge-Kutta method given by its tableau (A, c) and the place
of its constraints - TrapezoidalGGL is the 2-stage Lobatto IIIA with GGL, which the Python test confirms
(`_SolveRungeKutta` with the trapezoidal tableau equals `SolveTrapezoidalGGL`). So the C++ has one solver class whose
method is data, not four classes:

```
CSolverBase                                   unchanged: step loop, discontinuous iteration, output, restart
 ├─ CSolverStatic                             unchanged
 ├─ CSolverImplicitSecondOrderTimeInt         unchanged (generalized-alpha, Newmark, TrapezoidalIndex2)
 │   └─ ...UserFunction                       unchanged
 ├─ CSolverExplicitTimeInt                    unchanged, but its step size rule moves to StepSizeController
 └─ CSolverImplicitRungeKutta                 new: TrapezoidalGGL, LobattoIIIA4, LobattoIIIC4GGL, Radau3
       has  ImplicitRungeKuttaMethod          the tableau (A, c, s), the implicit stages, the constraint form
                                              (GGL | End), the order; four constexpr instances
       has  StageNewton                       the unknowns and the Newton iteration of one step (8.3)
       has  StepErrorEstimate                 oneStep (embedded trapezoidal) | twoSteps (the stages of the last
                                              accepted step kept), the RMS norm of the tolerances
       uses StepSizeController                shared with the explicit solver (RG20.8.2, #3245)
```

- **The method as data**: `ImplicitRungeKuttaMethod {name, s, A[s][s], c[s], implicitStages, constraintForm, order}`;
  the four instances are a table in one header, so a fifth method (e.g. a 3-stage Radau IIA of order 5) is a table
  entry, and the tests of the Python solvers carry over one to one.
- **`CSolverImplicitRungeKutta` overrides `Newton()`**, as the explicit solver does: the whole step - the stage
  unknowns, their Newton iteration, the error estimate - happens inside it, and the base class keeps the step loop,
  the reduction of a failed step, the discontinuous iteration (data coordinates by `PostNewton` after the stages
  converged, as in the Python solvers), the pre- and post-step functions, the files and the restart. Nothing of the
  existing solvers changes in RG20.7.
- **DynamicSolverType** gets `TrapezoidalGGL`, `LobattoIIIA4`, `LobattoIIIC4GGL`, `Radau3` (the hyphen of the Python
  name is not possible in an enum); `exudyn.solver.SolveDynamic` runs them like the others. The settings are those
  of `timeIntegration` (newton, automaticStepSize, the tolerances, minimumStepSize, stepSizeSafety,
  stepSizeMaxIncrease, discontinuous) plus one new setting `timeIntegration.errorEstimate` (oneStep | twoSteps, the
  default per method as in Python: twoSteps for the Runge-Kutta methods, oneStep for TrapezoidalGGL).

### 8.3 The stage Newton

- **Unknowns** (as in `_SolveRungeKutta`): per implicit stage the accelerations A_i (nODE2) and the ODE1 velocities
  Yd_i (nODE1); with GGL per implicit stage the multipliers z_i and mu_i (2 nAE); with End the two multipliers of the
  end constraints (2 nAE). Size `nStage = s_impl (nODE2 + nODE1) + 2 nAE` or `+ 2 s_impl nAE` - not `nSys`, so the
  class keeps its own vectors and its own `GeneralMatrix` (dense or sparse by `linearSolverType`), not the
  `SolverLocalData` ones.
- **Residual**: the stage states Q_i, V_i, Y_i from the unknowns and the start of the step, then per implicit stage
  the system residual of `CSystem` (the same calls as generalized-alpha: ODE2 right-hand side, mass matrix times A_i,
  C_q^T z_i, ODE1 right-hand side), and the constraint rows c and C_q v + c_t (c_t numerically, as in Python; no
  velocity-level implementation of the items is needed, advancedSolvers.md section 3.2).
- **Jacobian - simplified Newton**: the blocks M, K = -f_q, D = -f_v, the ODE1 blocks and C_q are evaluated once, at
  the start of the step (or kept over steps, as `useModifiedNewton` now), and the stage Jacobian is assembled from them
  with the coefficients of A and A^2 (a Kronecker structure, 2 implicit stages: a 2 x 2 block matrix of system-size
  blocks). The term H = (C_q v)_q is left out (section 3.2: the same errors, 3 to 27 % more iterations). The
  factorization is reused while the iterations converge; a full Newton with the Jacobians at each stage is the fallback
  when they do not (as `modifiedNewtonContractivity` decides now).
- **Sparse assembly**: the system Jacobian of `CSystem` already comes as sparse triplets; the stage Jacobian is the
  same triplets placed into the blocks, so its sparsity is that of the system times s_impl^2.
- Lie group nodes (`NodeRigidBodyRotVecLG`): the Python solvers refuse them; the C++ solver either refuses them too
  (first version) or composes the stage rotations with the exponential map as the explicit Lie group integrator does
  (later). Euler parameter nodes are ordinary: their norm is a constraint.

### 8.4 Step size control and error estimate

- **`StepSizeController`** (new, small, `src/Solver/StepSizeController.h`): the PI controller of `_ErrorStepSize`
  (RG20.8.1) with the settings of `timeIntegration` (safety, maximal increase and decrease, minimum step), the
  rejection and the step after a rejection; used by `CSolverImplicitRungeKutta` and, replacing its elementary rule, by
  the explicit ODE23 and DOPRI5 (RG20.8.2). The reduction after a failed Newton stays the base class path.
- **`StepErrorEstimate`**: `oneStep` - the difference to the embedded trapezoidal solution of the first and the last
  stage; `twoSteps` - the quadrature error against the polynomial through the stage values of the previous and this
  step, which needs the stage velocities and accelerations of the last accepted step kept (a few vectors of nODE2 +
  nODE1), the first step by `oneStep`. Both in the RMS norm of the tolerances, as the explicit solver.
- Automatic step size works for all four methods once it works for one: the estimate is a function of the tableau.
  Restricting it to TrapezoidalGGL and one Lobatto method saves no code; recommended: implemented for all, tested on
  TrapezoidalGGL and LobattoIIIA4 (the measurements of RG20.1 and RG20.2), the others by the same test with a
  looser check.

### 8.5a As implemented (RG20.7.1, #3261)

- `CSolverImplicitRungeKutta` (src/Solver/CSolverImplicitRungeKutta.h/.cpp) is a component of
  `CSolverImplicitSecondOrderTimeInt`, not a subclass of `CSolverBase`: the implicit solver runs its `Step()` in
  `Newton()` when `timeIntegration.solverType` is one of the four, so that the initial accelerations, the
  discontinuous iteration, the output, the restart, `MainSolverImplicitSecondOrder` and the implicit branch of
  `SolveDynamic` serve it without a new Main class. `StepSizeController.h` is the PI controller; ODE23 and DOPRI5 use
  it in RG20.8.2.
- The stage Newton: the Jacobians of the system (by q and by v, the mass matrix) at the last stage of the current
  iterate, placed into the stage matrix by the coefficients of A and A^2 as sparse triplets; mu is h^2 times its
  unknown; the rows scaled to entries of order 1 (ODE2 and ODE1 equations 1, constraints 1/h^2, velocity constraints
  1/h); the convergence by the norm of the unscaled residual, as generalized-alpha.
- Velocity-level constraints (`UsesVelocityLevel`) and the equations of a multiplier (an inactive constraint, a
  diagonal of the AE-AE block) are special rows: with GGL their equation at each implicit stage and mu = 0, at the end
  their equation at the last two stages.
- Measured on modelLibrary.py (constant steps h, h/2, h/4 against LobattoIIIA4 with h/16): orders 2.0, 4.0, 4.0, 3.0
  on the pendulum of mass points, the chain of rigid bodies on joints and on spring-dampers, the kinematic tree;
  2 to 4 iterations per step. Lie group nodes (the slider crank): Newton converges at h = 1e-3 and stalls at a
  floor of 2e-10 at h/16 - the stage Jacobian has no tangent operator (RG20.7.2). The genericDAE model fails as with
  TrapezoidalIndex2: its constraintUserFunction ignores velocityLevel.

### 8.6 Cases to decide or to keep in mind

- **Velocity-level and nonholonomic constraints** (rolling disc, `velocityLevel=True` of the joints, the
  `CoordinateConstraint` on velocities): the Python solvers refuse them (`_RefuseConstraintsBeyondPositions`). In C++
  they are common; they have no position equation, so GGL and End take only their velocity equation (index 2, at each
  implicit stage or at the end). Recommended: the C++ solver treats them so from the start; otherwise the new solvers
  cannot run the many models with rolling.
- **Lie group nodes** (8.3): refuse first, or the exponential map in the stages.
- **Data coordinates and contact** (the post-Newton step): as in Python, the discontinuous iteration around the whole
  step; with the automatic step a step rejected by the discontinuous iteration uses the base class reduction.
- **The initial accelerations**: as generalized-alpha computes them (`computeInitialAccelerations`), needed for the
  first stage of Lobatto IIIA and the trapezoidal estimate.
- **Output within the step** (RG20.4.2): the stage values give a dense output of the order of the method; the base
  class `FinishStep` needs a virtual `InterpolateState(t)` for the write times - a later extension of this structure,
  not needed for RG20.7.
