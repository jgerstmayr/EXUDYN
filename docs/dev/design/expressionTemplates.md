# Expression templates for the small linear algebra (design note)

A design note on the question whether expression templates should be enabled for Exudyn's small linear algebra
(`SlimVector`, `ConstSizeVector`, `Vector`, `ConstSizeMatrix`, `SlimMatrix`), and which ones. It builds on
[linalgFixedSize.md](linalgFixedSize.md) (compile-time sizes, `SlimMatrix`, #3456) and
[linalgBenchmark.md](linalgBenchmark.md) (measurements, L1-L6, #3417-#3419). Counts are word counts over `src/`
(2026-11-12) without `src/Autogenerated` (which calls none of the functions below), `src/Linalg` and `src/Tests` unless
said otherwise. No new timing was taken for this note.

The counts and line numbers were taken with `Matrix3D` as `ConstSizeMatrix<9>`; `Matrix6D` and `Matrix3D` are now
`SlimMatrix<6,6>` and `SlimMatrix<3,3>` (#3458, #3459, #3467); what is said here of `Matrix3D` as
`ConstSizeMatrix<9>` still holds for `Matrix3DF` and for the other `ConstSizeMatrix` sizes.

## 1. What an expression template is, and what it would replace

An expression template makes `a + s*b` return a small object that *describes* the sum instead of computing it; the
assignment `v = a + s*b` then runs one loop `v[i] = a[i] + s*b[i]` with no temporary vector. The same mechanism gives
lazy views such as a transposed matrix that is never copied: `Transposed(A) * v` reads `A(j, i)` directly.

Today every operator of the vector and matrix classes is eager: it returns a new object.

| expression | what runs now | temporaries |
|---|---|---|
| `SlimVector c = a + s*b` (`SlimVector.h:326-364`) | `s*b` into a stack temporary, then `a + temp` | 1 stack vector |
| `ConstSizeVector c = a + s*b` (`ConstSizeVector.h:392-497`) | as above; each temporary copies the whole `data[dataSize]` capacity plus the size | 1 stack vector of full capacity |
| `Vector c = a + s*b` (`Vector.h:453-498`) | as above | 1 **heap** allocation per operator |
| `A.GetTransposed() * v` (`ConstSizeMatrix.h:721`, `Matrix.h:724`) | copies A transposed (9 values for `Matrix3D`, a heap matrix for `Matrix`), then the product | 1 matrix |
| `A.GetTransposed() * (A1*w1 - A0*w0)` | 2 products, 1 difference, 1 transposed copy, 1 product | 4 |

Where these patterns occur:

| pattern | count | where it matters |
|---|---:|---|
| `X.GetTransposed() *` (outside Linalg/Tests) | 76 | ~30 in the force/residual code of joints and connectors: `CObjectJointRevoluteZ.cpp:70-98`, `CObjectJointPrismaticX.cpp:70-76`, `CObjectJointGeneric.cpp:125-155`, `CObjectJointHelicalZ.cpp:179-195`, `CObjectConnectorRigidBodySpringDamper.cpp:63-70`, `CObjectConnectorTorsionalSpringDamper.cpp:36-38`, `CObjectConnectorRollingDiscPenalty.cpp:87,203`, `CObjectConnector.cpp:544,650,657`, `CObjectRigidBody.cpp:656,666,696,761,789`; the rest are output variables (`value.CopyFrom(A.GetTransposed()*v)`, not hot), graphics (5), Pymodules (2) |
| `Vector3D`/`SlimVectorBase` declared from an expression with `+`/`-` and `*` | 144 | ANCF cables and beams, contact, joints (e.g. `CObjectANCFCable.cpp:369`: `integrationFactor * (EI * curvature + bendingDamping * curvature_t)`, 3 temporaries, `TReal` may be `AutoDiff`) |
| `Matrix3D x = ... * ... * ...` | 16 | e.g. `CMarkerBodiesRelativeRotationCoordinate.cpp:99` `Abasis.GetTransposed() * Arel * Abasis` |
| `... * (B * ...)` (nested product) | 147 | mostly `Matrix3D * (Matrix3D * Vector3D)`; products, not elementwise |
| `x += s * y`, `x -= s * y` (any type) | 176 / 37 | mostly scalar code; the vector cases in item code use `MultAdd` or loops |
| `.MultAdd(` | 44 | solvers (`CSolverExplicit.cpp:283-466`, `CSolverImplicitSecondOrder.cpp:929-1245`) on `ResizableVectorParallel`; 4 in item code |
| `Vector`/`Matrix` (heap) declared from an arithmetic expression in Solver, Main, System, Impl* | 1 | `CSolverImplicitRungeKutta.cpp:751` (a copy, not arithmetic) |
| hand-written `for (Index i = 0; i < 3 or 6; i++)` loops | 247 | many are vector expressions written out, e.g. the 6x6 spring and damper product `CObjectConnectorRigidBodySpringDamper.cpp:97-108` |

Two observations follow:

1. **Heap temporaries do not occur in hot code.** The solvers write their vector updates as `CopyFrom` + `MultAdd`
   sequences on `ResizableVectorParallel`, the item code uses stack types. The classic case for expression templates -
   avoiding heap allocations of `Vector c = a + b` - does not exist in Exudyn.
2. **What remains are stack temporaries of `SlimVector`/`ConstSizeMatrix<9>` and the transposed copies.** For `Real`
   these are 3-9 doubles; for `AutoDiff<12>` (the connector Jacobians, #2884) each `SlimVectorBase<AutoDiff<12>,3>`
   temporary is 39 doubles.

The symbolic module (`Symbolic.h`, `SymbolicVector.h`, `SymbolicMatrix.h`) builds expression trees at run time for
Python; it is a different mechanism and not touched here.

## 2. What is known about the cost of the temporaries

From `linalgBenchmark.md` §3.6 and `linalgFixedSize.md` §9 (ns per call, regular / fast module, after L1-L6):

| operation | Exudyn | Eigen (expression templates) | note |
|---|---:|---:|---|
| `SlimVector<3>`: `v = v + w*s` | 2.8 / 2.7 | 0.8 | one temporary; **3.5 times** |
| `SlimVector<3>`: `v = v.CrossProduct(w)*0.5 + w` | 4.4 / 4.3 | 4.2 / 4.3 | two temporaries; **equal** |
| `Matrix3D^T * Vector3D` by `GetTransposed()` | 9.8 / 5.1 (before L5) | 3.9 | transposed copy |
| `Matrix3D^T * Vector3D` by `MultMatrixTransposedVectorTemplate` | 7.1 / 7.6 | | no copy, run-time sizes |
| `SlimMatrix<3,3>^T * Vector3D` by `MultTransposedVector` | ~4.2 (as `SlimMatrix * v`) | 3.6 | no copy, compile-time sizes |
| `ConstSizeVector<6> +=` | 2.5 / 2.4 | 0.9 (`Matrix<6,1>`) | run-time size, not a temporary |

- The benchmark operations are dependency chains (the result feeds the next call), so the numbers are latency, not
  throughput. The cross-product case shows that two temporaries cost nothing measurable when the chain is
  latency-bound; the `v + w*s` case shows a gap of 2 ns whose cause is not established: the temporary going through
  memory, or the call structure of the lambda in the benchmark. A hand-fused loop in the same harness decides it
  (measurement M1 in §6).
- The transposed copy costs roughly 2-5 ns per call for `Matrix3D`. `v * A` (`ConstSizeMatrix.h:1061`, `SlimMatrix.h:519`)
  computes $\Am\tp\vv$ without the copy; linalgBenchmark.md §6.1 L5 recommends it for the hot places, and the
  replacement in the item code (64 places) is not done - because `v * A` does not read as $\Am\tp\vv$.
- Where the solver time goes (linalgFixedSize.md §8, rigid chain with `RigidBodySpringDamper`): the connector force 41 %
  of `ODE2RHS` - `Matrix3D` products, `RotationMatrix2RotXYZ` (atan2, asin), four transposed products with vectors and
  two 6x6 matrix-vector products. Elementwise vector expressions are a small part of it; the transposed products and the
  matrix sizes (RG5.2.4/RG5.2.5) are the larger part.

So the evidence supports **lazy transposition** clearly (a copy per call in ~30 hot places, and a readable
replacement for `v * A`), and leaves **elementwise fusion** open until M1 is measured.

## 3. Constraints

- **Bitwise results in the regular module.** Every floating-point sum must keep its order (start at 0, add in increasing
  index). MSVC does not contract `a*b+c` (`/fp:precise`, no `/fp:contract`); gcc/clang are built with
  `-ffp-contract=off` (`setup.py:454-458, 569`). On x64 there is no extended precision: a double stored into a temporary
  and a double kept in a register are the same double.
  - *Elementwise* expressions evaluated by an expression template compute, per element, exactly the operations of the
    eager version in the same order (`a[i] + (s*b[i])`): **the same bits**, provided contraction stays off. Fusing two
    statements into one expression would let a contracting compiler form an FMA where it did not before - which the
    build flags exclude.
  - *Products* keep their bits only if each entry still sums over k from 0 in increasing order. `Transposed(A) * v` reads
    `A(j, i) * v[j]` instead of `At(i, j) * v[j]`: the same products (multiplication is commutative in IEEE 754), the
    same order, **the same bits** - as `v * A` already does (#3418).
  - Negation is exact: `r += J^T(-f)` and `r -= J^T f` give the same bits.
- **Debuggability in VS2022** (CLAUDE.md invariant): a human steps from Python into the item code. An expression
  `v = a + s*b` with eager operators steps into `operator*`, then `operator+`, each a 3-line loop whose locals are
  plain `SlimVector`s in the watch window. With full expression templates the same line steps into node constructors and
  per-element `operator[]` of types like `SlimSum<SlimVectorBase<Real,3>, SlimScaled<Real, SlimVectorBase<Real,3>>>`,
  which the watch window cannot show as a vector. linalgFixedSize.md §4(c) rejects Eigen's fixed sizes partly for this
  reason.
- **Aliasing**: `v = A * v` is correct today because the product is computed into a temporary. A lazy product would read
  `v` while writing it. Products must stay eager (or be evaluated into a temporary, which is what they do now).
- **Dangling and surprising laziness**: `auto x = a + s*b;` stores the expression, not a vector: it references `a` and
  `b` (and possibly a destroyed temporary) and is evaluated later. This is the standard expression-template defect; it
  cannot be prevented by the compiler and would have to be a review rule.
- **Implicit conversions**: `SlimVectorBase(T scalarValue)` (`SlimVector.h:97`) is not `explicit`; with templated
  operators, `v + 1.` and similar expressions would find new, unintended overloads.
- **AutoDiff**: `AutoDiff` (`Utilities/AutomaticDifferentiation.h:44-260`) has eager operators returning 13-double
  values. An expression template over `SlimVectorBase<AutoDiff<12>,3>` removes the vector temporaries but not the
  `AutoDiff` temporaries per element.

## 4. Options

**(1) Full expression templates (Eigen-like)** for all vector and matrix types: elementwise nodes, lazy products,
transposed and block views, `noalias()`.
- Pros: no temporaries anywhere; one mechanism.
- Cons: the debuggability and `auto` problems of §3 in every item file; lazy products need an aliasing rule
  (`noalias`) that every author must know; compile time of the item files grows; the class hierarchy
  (`VectorBase` with virtual `SetNumberOfItems`, `LinkedDataVector`, `ResizableVector`, `ConstSizeVector`, `SlimVector`,
  `ConstSizeMatrix`, `SlimMatrix`, `MatrixBase`) needs a common expression base or a node per pair of types.
  Measured gain: Eigen's own small fixed sizes are slower than Exudyn's eager loops under MSVC except for `v + w*s`
  (linalgBenchmark.md §3.2, §3.8).
- Effort: high. Bits: elementwise the same; products the same only if every lazy product keeps the loop order.
- **Not recommended.**

**(2) A minimal set**: only constructs whose gain or readability is shown, each eager at the assignment, none with
`auto`-visible laziness beyond one statement:
- (2a) a **transposed view** `Transposed(A)` for the products `Transposed(A) * v` and `Transposed(A) * B` of the
  fixed-size types (`ConstSizeMatrix<9>`, `<16>`, `<36>`, `SlimMatrix`), evaluated at once by `operator*` into a
  concrete `SlimVector` / matrix;
- (2b) **fused elementwise expressions on `SlimVectorBase` only** (`+`, `-`, unary `-`, scalar `*`, `/`), materialized
  when assigned to or constructing a `SlimVectorBase` - only if measurement M1 shows a gain;
- (2c) **`MultAdd` on `SlimVectorBase`** (exists for `Vector`, `ConstSizeVector`, `ResizableVectorParallel`, not for
  `SlimVector`): `v.MultAdd(s, w)` = `v += s*w` without temporary - explicit, no template machinery.
- Products stay eager; no `noalias`.

**(3) None - explicit helpers instead**: keep the eager operators, use `MultTransposedVector(A, v)`
(`SlimMatrix.h:536`) or `EXUmath::MultMatrixTransposedVector...` for the transposed products, `MultAdd` for updates.
- Pros: nothing new to learn; already bitwise.
- Cons: `v * A` and `MultTransposedVector(A, v)` read worse than `Transposed(A) * v`; the 64 places of L5 stay as
  `GetTransposed()` because the helper spelling is clumsy.

## 5. Recommendation: enable two, measure the third

### 5.1 E1 - the transposed view (recommended, effort low)

```cpp
//! a view of the transposed of a fixed-size matrix: no copy; only operator* takes it, evaluated at once
template<class TMatrix>
class TransposedView
{
public:
	explicit TransposedView(const TMatrix& matrixInit) : matrix(matrixInit) {}
	const TMatrix& Matrix() const { return matrix; }
private:
	const TMatrix& matrix;
};

//! Transposed(A) of an lvalue: a reference view
template<class TMatrix>
inline TransposedView<TMatrix> Transposed(const TMatrix& matrix) { return TransposedView<TMatrix>(matrix); }

//! A^T * v for a 3x3 matrix: the kernel of v * A (ConstSizeMatrix.h:1061), the same bits as A.GetTransposed() * v
template<typename T, typename T2>
inline SlimVectorBase<T, 3> operator*(const TransposedView<ConstSizeMatrixBase<T, 9>>& At, const SlimVectorBase<T2, 3>& vector)
{
	return vector * At.Matrix();
}

//! A^T * B for 3x3 matrices: each entry sums over k in increasing order from 0, as GetTransposed() * B
template<typename T>
inline ConstSizeMatrixBase<T, 9> operator*(const TransposedView<ConstSizeMatrixBase<T, 9>>& At, const ConstSizeMatrixBase<T, 9>& B);

//! SlimMatrix: the existing kernels
template<typename T, typename T2, Index rows, Index columns>
inline SlimVectorBase<T, columns> operator*(const TransposedView<SlimMatrixBase<T, rows, columns>>& At, const SlimVectorBase<T2, rows>& v)
{
	return MultTransposedVector(At.Matrix(), v);   //SlimMatrix.h:536
}
template<typename T, Index inner, Index rows, Index columns>
inline SlimMatrixBase<T, rows, columns> operator*(const TransposedView<SlimMatrixBase<T, inner, rows>>& At, const SlimMatrixBase<T, inner, columns>& B)
{
	return MultTransposedMatrix(At.Matrix(), B);   //SlimMatrix.h:482
}
```

Item code then reads as the formula:

```cpp
//CObjectConnectorRigidBodySpringDamper.cpp:63-70
vLocPos    = Transposed(Ajoint) * (p1 - p0);
relRot     = Transposed(Ajoint) * A1all;
vLocAngVel = Transposed(Ajoint) * (A1*markers[1].angularVelocityLocal - A0*markers[0].angularVelocityLocal);
```

- The view is consumed in the same statement. `Transposed()` of an rvalue (`Transposed(GetRotationMatrix())`) must not
  return a reference view: an overload `Transposed(TMatrix&& matrix)` returns a view that **owns** a copy of the
  (untransposed) matrix, so `auto At = Transposed(node->GetRotationMatrix());` cannot dangle. The copy of a `Matrix3D`
  is 9 values, still cheaper than transposing it.
- No other operator accepts a `TransposedView` (no `+`, no conversion to a matrix): a misuse is a compile error, not a
  silent laziness. `GetTransposed()` stays for the places that need the matrix.
- Run-time sized matrices (`Matrix`, `ResizableMatrix`) do not get the view: their products write into an existing
  result (`EXUmath::MultMatrixTransposedVector...`), see the companion note
  [linalgTemplatesInventory.md](linalgTemplatesInventory.md).
- Bits: unchanged by construction (§3). The unit tests compare `Transposed(A) * x` with `A.GetTransposed() * x` bitwise
  for `ConstSizeMatrix<9>`, `<16>`, `<36>` and `SlimMatrix` of 3x3, 3x4, 4x3, 6x6, as `SlimMatrixUnitTests.h` does.
- Debugging: one call into a 3-line function; the view shows as a reference to the matrix in the watch window.
- After the switch of `Matrix3D`/`Matrix6D` to `SlimMatrix` (RG5.2.4/RG5.2.5) only the `SlimMatrix` overloads are needed.
- Expected: 2-5 ns per transposed product in about 30 hot places (joints, connectors, rigid-body loads); on the
  solver level a fraction of the 41 % share of the connector force - an estimate, to be shown by `exudev perf`.

### 5.2 E2 - `SlimVectorBase::MultAdd` (recommended, effort very low)

```cpp
//! add scalar * v to *this; the same bits as *this += scalar * v
inline void MultAdd(T scalar, const SlimVectorBase<T, dataSize>& v)
{
	for (Index i = 0; i < dataSize; i++) { data[i] += scalar * v.data[i]; }
}
```

The same function as `VectorBase::MultAdd` (`Vector.h:553`) and `ConstSizeVectorBase::MultAdd` (`ConstSizeVector.h:544`).
It is not an expression template, but it covers the accumulation pattern without machinery and keeps the vector types
uniform.

### 5.3 E3 - fused elementwise expressions on `SlimVectorBase` (decide after M1)

If M1 shows that the fused loop is faster in the shape of the item code (and not only in the benchmark chain), a
restricted design:

```cpp
//! base of an elementwise expression of fixed size; evaluated only by SlimVectorBase's constructor and assignment
template<class TExpression, typename T, Index dataSize>
struct SlimExpression
{
	T operator[](Index i) const { return static_cast<const TExpression&>(*this)[i]; }
};

//! a + b, elementwise; leaves (SlimVectorBase) held by reference, sub-expressions by value
template<class TLeft, class TRight, typename T, Index dataSize>
struct SlimSum : SlimExpression<SlimSum<TLeft, TRight, T, dataSize>, T, dataSize>
{
	typename SlimOperand<TLeft>::Type left;    //const& for a SlimVectorBase, a copy for an expression node
	typename SlimOperand<TRight>::Type right;
	T operator[](Index i) const { return left[i] + right[i]; }
};
//SlimDifference, SlimNegation, SlimScaled (scalar * expression) alike

//in SlimVectorBase:
template<class TExpression>
SlimVectorBase(const SlimExpression<TExpression, T, dataSize>& expression)
{
	for (Index i = 0; i < dataSize; i++) { data[i] = expression[i]; }   //one loop, the operations of the eager version per element
}
```

- Scope: `SlimVectorBase` only (`Vector3D`, `Vector6D`, `SlimVectorBase<TReal,3>`), the four elementwise operators and the
  scalar multiplication/division; `CrossProduct`, `operator*` (scalar product) and all matrix products stay eager and
  return `SlimVectorBase`.
- Aliasing: `v = v + w*s` is safe for elementwise operations (each element reads only its own index).
- `auto`: `auto x = a + s*b` holds references to `a` and `b` and is evaluated later; a review rule ("no `auto` for vector
  expressions") is needed. This is the cost of E3 that E1 and E2 do not have.
- `SlimVectorBase(T scalarValue)` should become `explicit` first, so that a scalar does not convert into an operand.
- Bits: the same (§3).
- Effort: medium (the node types, the materialization, conversions to `ConstSizeVector`/`Vector`, `AutoDiff` as T), and
  a check of the 144 expression lines that they still compile and give the same bits (test suite, regular module).

E3 is not recommended unless M1 shows a gain of at least 2 times on `SlimVector<3>` expressions **and** a share of
those expressions in a profiled `ODE2RHS` that makes the gain visible in `exudev perf`.

## 8. Done: E1, the transposed view (RG5.2.7.2, #3479, 2026-11-12)

`src/Linalg/SlimMatrix.h`: `TransposedView` (an lvalue, by reference) and `TransposedCopy` (an rvalue, the matrix kept),
`Transposed()` for both, and `operator*` with a `SlimVectorBase` and a `SlimMatrixBase`, through `MultTransposedVector`
and `MultTransposedMatrix`. Only `SlimMatrix` gets the view: `Matrix3D` and `Matrix6D` are `SlimMatrix` (#3459), and the
run-time sized matrices keep the `EXUmath` kernels. The accessor is `GetMatrix()`, as `Matrix` is a type name. Unit
test case in `SlimMatrixUnitTests.h`: 3x3, 3x4, 6x6 and an rvalue, bitwise against `A.GetTransposed() * x`. The item
code is unchanged; its about 30 places are RG5.2.7.3.

## 9. The measurements M1a-M1e (RG5.2.7.1, #3487, 2026-11-13)

The cases of section 6 are the group `temporaries` of `RunLinalgBenchmark`; the table is
[linalgBenchmark.md](linalgBenchmark.md) section 3.11. What they decide:

- **E3 for `Real` does not pay.** `c = a*s1 + b*s2 - d` on `SlimVector<3>` takes 0.77 ns with the eager operators and with
  one hand-written loop alike (fast module); the compiler removes the temporaries of 3 doubles. The condition of section
  5.3 (a gain of at least 2 times) is not met.
- **For `AutoDiff<12>` the temporaries cost 3.6-4.4 times** (47-69 ns against 13-16 ns). Fused expressions would pay
  there, but only there: whether they pay in a simulation depends on the share of `SlimVectorBase<AutoDiff<12>,3>`
  expressions in the analytic connector Jacobians (#2884), not measured yet. A cheaper remedy than E3 for those few
  places is writing them as loops or with `MultAdd`.
- E1 is confirmed for products of matrices (`Transposed(A) * B` -18 %); for `Transposed(A) * x` on `SlimMatrix<3,3>` it
  is neutral, as `exudev perf` showed after RG5.2.7.3. E2 (`MultAdd`) is 5 times faster than `v = v + w*s` in a chain.
