# User functions: vectors and matrices at the C++/Python boundary - analysis and proposal

The analysis of revision2026c step RG12.3.1 (#2996), sections 1 to 4: where a user function with vector arguments
allocates memory, what that costs against the call itself, and the options. The proposal of RG12.3.3 (2026-10-16),
sections 5 to 10: what the Exudyn vector and matrix classes must be able to do so that the same user function
interface serves Python and symbolic user functions without allocations, the call interface, the symbolic evaluation,
helpers, and the revision of the user items, ObjectUserBody first. The measurement is
[userFunctionBoundary.py](userFunctionBoundary.py), next to this document; the earlier measurement of the cost of a call
into Python is in [pythonUserItems.md](pythonUserItems.md), section 7.

The maintainer's question (2026-10-16): which vector and matrix classes, or what must they be able to do, such that
the interface is smoothest for Python and for symbolic user functions - ideally with no memory allocation on the
Exudyn side in either; the symbolic path has the priority for efficiency, while for Python a copy of a small vector
does not matter. `std::vector`, the present means of transport, could be passed as const reference and only link to
the memory of the internal vector - but how to do this best.

Conditions, from the maintainer (2026-10-15): Python user functions run serially - the solver calls them from the main
thread, one at a time -, so the GIL is no question for them; symbolic user functions are the ones that may run in
parallel (RG7.8) and where the boundary may be the bottleneck.

## 1. Which user functions take vectors

42 user function parameters of the items (objects, loads, sensors, MainSystem); 28 of them have a symbolic version
(src/Autogenerated/PySymbolicUserFunctionSet.h). The ones without are those that return a matrix (`massMatrix...`,
`jacobian...`, `positionJacobian...`, `rotationMatrix...`, `rotationJacobian...` - returned as `py::object` and
converted by `PyMatrixContainer` or `NumPy2Matrix`), `sensorUserFunction` and the graphics user functions.

The user function parameters of the items come in 26 pairs of name and signature; 14 of them take or return
`StdVector`, a `std::vector<Real>` of the size of the item (`src/Autogenerated/PythonUserFunctionsTemplates.h`):

| user function | items |
|---|---|
| `forceUserFunction`, `massMatrixUserFunction`, `jacobianUserFunction` (q, q_t) | ObjectGenericODE2, ObjectFFRF, ObjectFFRFreducedOrder, ObjectKinematicTree, ObjectUserBody |
| `rhsUserFunction` (q) | ObjectGenericODE1 |
| `positionUserFunction`, `positionJacobianUserFunction`, `rotationMatrixUserFunction`, `rotationJacobianUserFunction`, `outputVariableUserFunction` (q) | ObjectUserBody |
| `constraintUserFunction`, `jacobianUserFunction` (q, q_t) | ObjectConnectorCoordinateVector |
| `postNewtonStepUserFunction` | ObjectConnectorRigidBodySpringDamper |
| `sensorUserFunction` (factors) | SensorUserFunction |

The other 12 pairs take scalars and the fixed-size types `StdVector3D`, `StdVector6D`, `StdMatrix3D`, `StdMatrix6D`
(`std::array`), which need no heap memory in C++.

## 2. The path of one call

`ObjectGenericODE2::ComputeODE2LHS` with a `forceUserFunction`, as an example of all of them
(src/ImplObjects/CObjectGenericODE2.cpp, src/System/evaluateUserFunctions.cpp, src/Autogenerated/PySymbolicUserFunctionSet.h,
src/Linalg/SymbolicUtilities.h). The coordinates are gathered into the members `tempCoordinates`, `tempCoordinates_t`
(Exudyn `Vector`s, no allocation), then:

| # | step | heap allocations |
|---|---|---|
| 1 | `Vector` to the `const StdVector&` parameter of `EvaluateUserFunctionForce`: `operator std::vector<T>()` | 2 (q, q_t) |
| 2 | the `std::function<StdVector(..., StdVector, StdVector)>` takes its vectors **by value** | 2 |
| **Python** | | |
| 3P | pybind11 converts each `std::vector<Real>` into a Python **list** of `float`s (stl.h) | 2 lists + 2n floats |
| 4P | the returned list or array into a `std::vector<Real>` | 1 |
| **symbolic** | | |
| 3S | the generated lambda takes its vectors by value, `EvaluateStdVector(Args... args)` again | 2 |
| 4S | `processArgument(const ResizableConstVector&)` from a `std::vector`: the constructor `ResizableConstVectorBase(const std::vector<T>)` takes its argument by value, and allocates above 7 items | 2 (+2 above 7) |
| 5S | the expression tree; `EvaluateReturnVector()` returns a `ResizableConstVector`; `(StdVector)` cast | 1 (+1 above 7, + temporaries of the tree) |
| **both** | | |
| 6 | `(Vector)` of the `StdVector`: `VectorBase(const std::vector<T> vector)` takes it by value, then allocates | 2 |
| 7 | `force = ...` into the local `Vector userForce`: Vector has no move assignment, it copies | 1 |

About a dozen heap allocations per call for a symbolic function, 8 plus the Python objects for a Python function,
from reading the code. Most of them are copies made because arguments are taken by value.

**Inside the symbolic evaluation** (src/Linalg/SymbolicVector.h) there is a second source: every node of a vector
expression returns its value by value - `ResizableConstVector Evaluate() const` -, a named vector returns a copy of
its stored vector, an operator such as `+` evaluates both operands into new vectors and returns a third. `-k*q - d*q_t`
makes about five vectors per call; up to 7 items they are in the local memory of `ResizableConstVector`, above on the
heap. The stored values of the named variables (`argRealList`) belong to the function object: one evaluation at a
time.

## 3. Measured (Windows, Python 3.13, V1.13.92, best of 3; solver timer `userFunctions`, the call with its conversions)

ObjectGenericODE2.forceUserFunction, microseconds per call:

| n | symbolic | Python, computes a list | Python, returns a prepared list | Python, returns a prepared numpy array |
|---:|---:|---:|---:|---:|
| 1 | 0.306 | 0.636 | 0.453 | 0.484 |
| 5 | 0.329 | 0.782 | 0.539 | 0.641 |
| 7 | 0.332 | 0.862 | 0.571 | 0.700 |
| 10 | 0.454 | 0.991 | 0.645 | 0.811 |
| 100 | 0.668 | 5.13 | 2.66 | 4.28 |
| 1000 | 4.17 | 47.3 | 29.0 | 53.3 |

The symbolic column above 7 is measured after #2998 (the Python columns of n = 100, 1000 vary by up to a factor 1.8
between runs); from 8 items the symbolic vectors are on the heap.

The reference with scalar arguments only, LoadCoordinate.loadUserFunction: symbolic 0.035 to 0.050, Python 0.20 to 0.36
(two runs). A copy of a small `std::vector<double>` costs about 6 ns under Linux in a tight loop; the Windows heap
is slower.

- **Symbolic: about 90 % of a call with vectors is the boundary**: 0.31 against 0.035 to 0.050 with scalars - for an
  expression as small as `-k*q`. This is where the allocations matter.
- **Python: the boundary is about 0.25 microseconds plus 25 ns per value**, for the lists in and the result out; the
  Python body comes on top (0.18 at n = 1, 18 at n = 1000 for the list comprehension). For small n the call into
  Python itself dominates; for large n the conversion of the lists.
- **A Python function gets lists, not numpy arrays** (`type(q)` is `list`): `q` must be converted by the user before
  `K @ q`, and returning a numpy array is slower than returning a list (pybind11 converts it item by item).
- **Symbolic vector functions above 7 items crashed** (#2998, fixed): `ResizableConstVector::SetNumberOfItems` pointed
  `data` to its local buffer of 7 when the size was set again - the second call wrote past it, the destructor deleted
  it. Found by this measurement.

## 4. Options

| | option | removes | effort | risk |
|---|---|---|---|---|
| A | `const StdVector&` in the `std::function` signatures, the generated symbolic lambdas and `EvaluateStdVector`; `const std::vector<T>&` in the constructors of `VectorBase` and `ResizableConstVectorBase` | steps 2, 3S, the by-value copies of 4S and 6: 6 to 8 of the allocations | small: the generators and two constructors | none for users; pybind11 accepts const references in `std::function` |
| B | per item, persistent `StdVector` buffers for the arguments (filled with `assign`, capacity kept) instead of the conversion of step 1 | step 1 | small per item | a buffer per item; fine serially, and an item is evaluated by one thread at a time |
| C | a direct path for symbolic functions: the arguments as `LinkedDataVector` (views of the coordinates) into the named vectors, the result evaluated into a caller's `Vector&` - a second call interface of `PythonUserFunctionBase` for the symbolic type, beside the `std::function` | all allocations of the symbolic path: expected near the scalar 0.05 microseconds | medium: the 14 vector signatures in the generator | the shared argument storage of a symbolic function (`argRealList`) then needs one per thread for RG7.8 |
| D | Python: read-only numpy arrays that view the C++ buffers ("linking") instead of lists; the result accepted as numpy and copied once into the `Vector` | step 3P (O(n)), step 4P and 6 for numpy results | medium: a type caster or explicit `py::array` arguments | a stored `q` changes with the next call (it is a view); read-only flag and a sentence in the documentation; a list user function still works with numpy input |
| E | move assignment for `Vector` | step 7 | small | the same care as #2999: no move through a base reference into a resizable or linked vector |

A changes no behaviour and halves the allocations of both kinds; C is where the symbolic functions gain most; D is the
"linking" for Python, worthwhile above about 100 values, and gives users numpy arrays, as they expect. B is contained
in C and D.

## 5. What the vector and matrix classes must be able to do

The requirements that follow from sections 2 and 3, independent of a class name:

| | requirement | why | today |
|---|---|---|---|
| R1 | a **read-only view** of a vector or matrix: pointer and size (rows, columns), no ownership, cheap to make, made from any Exudyn vector or matrix, a segment of one, a `std::vector`, a raw pointer | the arguments of a user function are always existing memory: the coordinates of an item, a marker's data | `LinkedDataVector`, `LinkedDataMatrix` (derive from `VectorBase`, `MatrixBase`, with virtual functions, writable) |
| R2 | an **output that keeps its memory**: written into by size, grows only when needed, never shrinks its capacity | the result of a user function goes into memory of the item that is reused every call | `ResizableVector`, `ResizableMatrix`; copy assignment consistent since #2999 |
| R3 | **copy from anything** into R2, in one pass: an Exudyn vector or view, a `std::vector`, a numpy array (buffer protocol, contiguous `float64`: one `memcpy`), a list | the result of a Python user function | `CopyFrom` for Exudyn types; numpy and lists through `std::vector` (two copies) |
| R4 | **a numpy view of R1**, read-only, without copying | Python arguments without the O(n) list | `GetSystemStateDict(reference=True)` builds such views; not for user functions |
| R5 | **moves that are safe** through a base reference | results passed back | matrices since #2999; `Vector` has no move assignment (copies: safe, one allocation) |
| R6 | for symbolic: a **named variable that links** to R1 instead of holding a copy, and **evaluation into a buffer** owned by the expression node | the expression tree without allocations | named variables copy; nodes return by value |
| R7 | per-thread evaluation state for symbolic functions | RG7.8: symbolic items in parallel | one `argRealList` per function |

The fixed-size types (`SlimVector`, `ConstSizeVector`, `ConstSizeMatrix`, `std::array` as `StdVector3D`, ...) already
need no heap memory and stay as they are.

## 6. Proposal: the linalg components

1. **R1: the arguments of a user function are `const Vector&` and `const Matrix&`** (maintainer 2026-10-16) - the
   base classes `VectorBase<Real>`, `MatrixBase<Real>`, of which `Vector`, `ResizableVector`, `LinkedDataVector` (and
   `Matrix`, `ResizableMatrix`, `LinkedDataMatrix`) are; the item passes what it has without a conversion: its own
   buffer, or a `LinkedDataVector` view of a part of a system vector. Memory that is no Exudyn vector - a
   `std::vector`, a raw pointer, a `ConstSizeVector` or `SlimVector`, which are no `VectorBase` - is wrapped in a
   `LinkedDataVector` first; added for it: constructors from `const std::vector<Real>&` and from `(const Real*, Index)`
   without `const_cast` at the call site.
2. **R2: the result is `Vector&` (`Matrix&`)**, in which the item usually passes a `ResizableVector` (`ResizableMatrix`):
   `SetNumberOfItems` is virtual, so a resizable vector keeps its capacity, a `Vector` allocates, and a
   `LinkedDataVector` of the right size receives the result in place - e.g. directly in a part of a system vector. With
   R5 for `Vector`: a move assignment that exchanges memory only between two plain `Vector`s and copies otherwise - the
   rule of #2999 for matrices.
3. **R3: `CopyFrom(const std::vector<Real>&)` on all vectors, and `EPyUtils::CopyFromPython(const py::handle&,
   ResizableVector&)` / `(..., ResizableMatrix&)`**: a numpy array through the buffer protocol (contiguous `float64`:
   one `memcpy`; otherwise `py::array_t<Real, py::array::forcecast>`), a list or tuple item by item. The constructors
   that take `std::vector<T>` by value take it by const reference.
4. **R4: `EPyUtils::ToNumpyView(const Vector&)` / `(const Matrix&)`**: a `py::array_t<Real>` with the data pointer
   and a dummy base object (no copy, no ownership), flagged not writeable. Valid during the call.

## 7. Proposal: the call of a user function

**Today** the item calls `parameters.forceUserFunction.userFunction(mbs, t, i, q, q_t)`, a `std::function` with
`StdVector` arguments and result, into which both kinds are wrapped: the Python function by pybind11, the symbolic
function as a generated lambda.

**Proposed**: `PythonUserFunctionBase<UFT>` gets, per signature and generated with it, a call that writes into the
caller's buffer and dispatches on the kind:

```cpp
//generated for forceUserFunction: (mbs, t, itemNumber, q, q_t) -> vector
void Evaluate(Vector& result, const MainSystem& mbs, Real t, Index itemNumber,
              const Vector& q, const Vector& q_t) const
{
    if (ufType == UserFunctionType::Symbolic)  //links q, q_t into the named vectors, evaluates into result: no allocation
    { symbolicFunction->Evaluate(result, mbs, t, itemNumber, q, q_t); }
    else                                       //views for Python (R4), one copy of the result (R3)
    { EPyUtils::CopyFromPython(pythonFunction(mbs, t, itemNumber, ToNumpyView(q), ToNumpyView(q_t)), result); }
}
```

- the item keeps `q`, `q_t` and `result` as its own buffers, or takes them from `TemporaryComputationData` where the
  function has it (one per thread);
- the `std::function` member stays for what needs it (the dictionary of an item, calling a user function from
  Python), and leaves the hot path;
- the generator (tools/generators, the user function declarations in definitions/) emits the `Evaluate` per
  signature from the argument types it has: `StdVector` becomes `const Vector&`, a result `StdVector` becomes
  `Vector&`, matrices `const Matrix&` and `Matrix&` or `MatrixContainer&`; `StdVector3D` and the other fixed sizes stay;
- `UserFunctionExceptionHandling` and the solver timer wrap `Evaluate` as they wrap the call now.

## 8. Proposal: symbolic evaluation without allocations

1. **Linked named variables (R6)**: `VectorExpressionNamedReal` can hold a `LinkedDataVector` to the argument instead
   of a copy; `processArgument(const Vector&)` sets the link to the memory of the argument - no copy, the value is read
   where it is.
   Matrices the same (`MatrixExpressionNamedReal`).
2. **Evaluation into node buffers**: `const ResizableConstVector& EvaluateRef() const` beside `Evaluate()`: a named
   variable returns its (linked) memory, an operator evaluates into a `mutable ResizableConstVector` member of the node
   and returns it - allocated at the first call, reused after (the sizes do not change between calls). The result is
   copied once into the caller's buffer. Scalars are not affected.
3. **Per-thread state (R7)**: the node buffers and the linked arguments are state of one evaluation; for RG7.8 the
   function keeps one set per thread (indexed by the thread number of the task manager), or evaluates a copy of the
   tree per thread - to be decided with RG7.8.

Expected: a symbolic `forceUserFunction` near the cost of the scalar one (0.035 to 0.050 microseconds) plus the
arithmetic, against 0.31 to 4.2 microseconds now (n = 1 to 1000).

## 9. Proposal: Python user functions

- `q`, `q_t` arrive as **read-only numpy arrays** that view the coordinates (R4) instead of lists: no O(n) conversion,
  and `K @ q` works without `np.array(q)`. A function written for lists keeps working where it reads (`q[i]`, `len(q)`,
  iteration, `-k*x for x in q`); it fails where it writes into `q` or uses list operations (`q + [...]`, `q.append`) -
  rare in user functions, but a change of behaviour: with a switch for the transition (e.g.
  `exu.special.userFunctions.vectorsAsLists`) or with version 2.0.
- the result: numpy arrays copied with one `memcpy` (R3), lists item by item - no longer through `std::vector`.
- a view is valid during the call; a function that keeps `q` (in a closure, for the next call) must copy it:
  `q.copy()`. One sentence in the documentation of every such user function, written once in the general section on
  user functions.
- expected: the boundary independent of n, about 0.3 microseconds for two arrays, against 29 microseconds at n = 1000
  now; for small n about what the lists cost now.

## 10. Proposal: the user items, ObjectUserBody first (RG7.3.4)

The interface above decides most of the points of RG7.3.4:

| point of RG7.3.4 | with this proposal |
|---|---|
| (1) static functions | members: `ConfigurationTime` becomes a function of `CSystemData` (the time of a configuration, needed elsewhere too) |
| (2) `EvaluateMatrix(which)` | three generated `Evaluate` calls of their user functions, each into a `ResizableMatrix&`; one private helper checks the size |
| (3) `StdVector` inside | the coordinates in `ResizableVector` buffers of the item; the user function gets views |
| (4) `GetODE2Size` loop | the coordinate offsets per node kept at `Assemble`, as ObjectGenericODE2 does |
| (5) `GetObjectNumber` search | the object number known to every `CObject` from `AddObject` (also for the other items with user functions) |
| (6) derivative of J^T f | the step from `newton.numericalDifferentiation`; optional user function for it later |
| (7) double evaluations | `GetDisplacement` from one position evaluation and the reference position stored at `Assemble` |
| (8) errors of a wrong size | one check in the generated `Evaluate`: `PyError` with the name of the user function and the sizes |
| (9)-(12) ObjectGenericODE2 | the commented code removed; the Jacobian through `CopyOrAddTripletsWithFactor` in both modes; the coordinate buffers as in (3) |
| (13) displacement or total coordinates | waits for RG13 (total coordinates in the system data and the solvers, maintainer 2026-10-16): until then both stay as they are - ObjectGenericODE2 gives displacements, ObjectUserBody total coordinates - and each description says which; the efficiency of forming the total coordinates is no criterion of this proposal |
| (14) MainSystem argument | inside the generated `Evaluate` (the item has `cSystemData->GetMainSystemBacklink()`) |
| (15) gathering coordinates | one function `CObjectBody::GatherCoordinates(ResizableVector& q, ResizableVector& q_t, configuration, withReference)` for GenericODE2, GenericODE1, UserBody, KinematicTree, FFRF |
| (16) the matrix copy | done (#2999) |
| (17) visualization cache | to decide (main thread or not drawn) |

**Helpers for users**: none needed for the interface itself; `exudyn.advancedUtilities.CreateSymbolicUserFunction`
stays the way to make a symbolic function. The documentation gets one section on the arguments (views, valid during
the call) and the results (numpy or list, copied).

## 11. Steps

1. A and R3, R5 (const references, `CopyFrom(std::vector)`, `Vector` move assignment, the by-value constructors):
   mechanical, no change for users; measured again with userFunctionBoundary.py.
2. Section 8, symbolic evaluation into node buffers and linked named variables, with the generated `Evaluate`
   (section 7) for the symbolic kind: the gain where it matters.
3. Section 9, the Python views: a decision (the change of `q` from list to numpy).
4. Section 10 with RG7.3.4, on top of 1 to 3.
5. Matrices (`massMatrixUserFunction`, `jacobianUserFunction`, the Jacobians of ObjectUserBody): the same scheme with
   `const Matrix&` arguments and `Matrix&` / `MatrixContainer&` results; #1864 belongs here.
