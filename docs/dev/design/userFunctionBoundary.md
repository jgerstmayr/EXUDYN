# User functions: vectors at the C++/Python boundary - pre-analysis

The pre-analysis of revision2026c step RG12.3.1 (#2996): where a user function with vector arguments allocates memory,
what that costs against the call itself, and what passing the vectors without copies ("linking") would take. The
measurement is [userFunctionBoundary.py](userFunctionBoundary.py), next to this document; the earlier measurement of
the cost of a call into Python is in [pythonUserItems.md](pythonUserItems.md), section 7.

Conditions, from the maintainer (2026-10-15): Python user functions run serially - the solver calls them from the main
thread, one at a time -, so the GIL is no question for them; symbolic user functions are the ones that may run in
parallel (RG7.8) and where the boundary may be the bottleneck.

## 1. Which user functions take vectors

The user function parameters of the items come in 26 pairs of name and signature; 14 of them take or return
`StdVector`, a `std::vector<Real>` of the size of the item (`src/Autogenerated/PythonUserFunctionsTemplates.h`):

| user function | items |
|---|---|
| `forceUserFunction`, `massMatrixUserFunction`, `jacobianUserFunction` (q, q_t) | ObjectGenericODE2, ObjectFFRF, ObjectFFRFreducedOrder, ObjectKinematicTree, ObjectUserBody |
| `rhsUserFunction` (q) | ObjectGenericODE1 |
| `positionUserFunction`, `positionJacobianUserFunction`, `rotationMatrixUserFunction`, `rotationJacobianUserFunction`, `outputVariableUserFunction` (q) | ObjectUserBody |
| `constraintUserFunction`, `jacobianUserFunction` (q, q_t) | ObjectConnectorCoordinateVector |
| `postNewtonStepUserFunction` | ObjectConnectorRigidBodySpringDamper |
| `sensorUserFunction` (factors) | SensorUserFunction |

The other 12 pairs take scalars and the fixed-size types `StdVector3D`, `StdVector6D`, `StdMatrix3D`, `StdMatrix6D`
(`std::array`), which need no heap memory in C++.

## 2. The path of one call

`ObjectGenericODE2::ComputeODE2LHS` with a `forceUserFunction`, as an example of all of them
(src/ImplObjects/CObjectGenericODE2.cpp, src/System/evaluateUserFunctions.cpp, src/Autogenerated/PySymbolicUserFunctionSet.h,
src/Linalg/SymbolicUtilities.h). The coordinates are gathered into the members `tempCoordinates`, `tempCoordinates_t`
(Exudyn `Vector`s, no allocation), then:

| # | step | heap allocations |
|---|---|---|
| 1 | `Vector` to the `const StdVector&` parameter of `EvaluateUserFunctionForce`: `operator std::vector<T>()` | 2 (q, q_t) |
| 2 | the `std::function<StdVector(..., StdVector, StdVector)>` takes its vectors **by value** | 2 |
| **Python** | | |
| 3P | pybind11 converts each `std::vector<Real>` into a Python **list** of `float`s (stl.h) | 2 lists + 2n floats |
| 4P | the returned list or array into a `std::vector<Real>` | 1 |
| **symbolic** | | |
| 3S | the generated lambda takes its vectors by value, `EvaluateStdVector(Args... args)` again | 2 |
| 4S | `processArgument(const ResizableConstVector&)` from a `std::vector`: the constructor `ResizableConstVectorBase(const std::vector<T>)` takes its argument by value, and allocates above 7 items | 2 (+2 above 7) |
| 5S | the expression tree; `EvaluateReturnVector()` returns a `ResizableConstVector`; `(StdVector)` cast | 1 (+1 above 7, + temporaries of the tree) |
| **both** | | |
| 6 | `(Vector)` of the `StdVector`: `VectorBase(const std::vector<T> vector)` takes it by value, then allocates | 2 |
| 7 | `force = ...` into the local `Vector userForce`: Vector has no move assignment, it copies | 1 |

About a dozen heap allocations per call for a symbolic function, 8 plus the Python objects for a Python function,
from reading the code. Most of them are copies made because arguments are taken by value.

## 3. Measured (Windows, Python 3.13, V1.13.92, best of 3; solver timer `userFunctions`, the call with its conversions)

ObjectGenericODE2.forceUserFunction, microseconds per call:

| n | symbolic | Python, computes a list | Python, returns a prepared list | Python, returns a prepared numpy array |
|---:|---:|---:|---:|---:|
| 1 | 0.306 | 0.636 | 0.453 | 0.484 |
| 5 | 0.329 | 0.782 | 0.539 | 0.641 |
| 7 | 0.332 | 0.862 | 0.571 | 0.700 |
| 10 | - | 0.991 | 0.645 | 0.811 |
| 100 | - | 5.13 | 2.66 | 4.28 |
| 1000 | - | 47.3 | 29.0 | 53.3 |

The reference with scalar arguments only, LoadCoordinate.loadUserFunction: symbolic 0.035 to 0.050, Python 0.20 to 0.36
(two runs). A copy of a small `std::vector<double>` costs about 6 ns under Linux in a tight loop; the Windows heap
is slower.

- **Symbolic: about 90 % of a call with vectors is the boundary**: 0.31 against 0.035 to 0.050 with scalars - for an
  expression as small as `-k*q`. This is where the allocations matter.
- **Python: the boundary is about 0.25 microseconds plus 25 ns per value**, for the lists in and the result out; the
  Python body comes on top (0.18 at n = 1, 18 at n = 1000 for the list comprehension). For small n the call into
  Python itself dominates; for large n the conversion of the lists.
- **A Python function gets lists, not numpy arrays** (`type(q)` is `list`): `q` must be converted by the user before
  `K @ q`, and returning a numpy array is slower than returning a list (pybind11 converts it item by item).
- **Symbolic vector functions above 7 items crash** (#2998): `ResizableConstVector::SetNumberOfItems` points `data` to
  its local buffer of 7 when the size is set again - the second call writes past it, the destructor deletes it. Found
  by this measurement; the symbolic column ends at 7 because of it.

## 4. Options

| | option | removes | effort | risk |
|---|---|---|---|---|
| A | `const StdVector&` in the `std::function` signatures, the generated symbolic lambdas and `EvaluateStdVector`; `const std::vector<T>&` in the constructors of `VectorBase` and `ResizableConstVectorBase` | steps 2, 3S, the by-value copies of 4S and 6: 6 to 8 of the allocations | small: the generators and two constructors | none for users; pybind11 accepts const references in `std::function` |
| B | per item, persistent `StdVector` buffers for the arguments (filled with `assign`, capacity kept) instead of the conversion of step 1 | step 1 | small per item | a buffer per item; fine serially, and an item is evaluated by one thread at a time |
| C | a direct path for symbolic functions: the arguments as `LinkedDataVector` (views of the coordinates) into the named vectors, the result evaluated into a caller's `Vector&` - a second call interface of `PythonUserFunctionBase` for the symbolic type, beside the `std::function` | all allocations of the symbolic path: expected near the scalar 0.05 microseconds | medium: the 14 vector signatures in the generator | the shared argument storage of a symbolic function (`argRealList`) then needs one per thread for RG7.8 |
| D | Python: read-only numpy arrays that view the C++ buffers ("linking") instead of lists; the result accepted as numpy and copied once into the `Vector` | step 3P (O(n)), step 4P and 6 for numpy results | medium: a type caster or explicit `py::array` arguments | a stored `q` changes with the next call (it is a view); read-only flag and a sentence in the documentation; a list user function still works with numpy input |
| E | move assignment for `Vector` | step 7 | small | the same care as #2999: no move through a base reference into a resizable or linked vector |

A changes no behaviour and halves the allocations of both kinds; C is where the symbolic functions gain most; D is the
"linking" for Python, worthwhile above about 100 values, and gives users numpy arrays, as they expect. B is contained
in C and D.

## 5. Proposal

1. #2998 first (a crash, one line).
2. A (and the `VectorBase` constructor of step 6): mechanical, measured again with this script.
3. C for the symbolic functions, together with RG7.8 (parallel symbolic items), which needs the per-thread argument
   storage anyway.
4. D for the Python functions, as a decision of its own: numpy views change what `q` is in a user function.

Not covered: matrices at the boundary (`massMatrixUserFunction`, `jacobianUserFunction` return `py::object` or
`NumpyMatrix` and go through `PyMatrixContainer`) - one level larger, and #1864 (a MatrixContainer that links a numpy
matrix) is about them.
