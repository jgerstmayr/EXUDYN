# Solving the systems of one SystemContainer in parallel

A design note of revision2026c step RG5.10 (#3433): what the systems of one `SystemContainer` and their solvers share,
which would race if each system's solver ran on a thread of its own at the same time. This is the pre-analysis (step
RG5.10.1); the design follows from it.

Use case: a model of independent parts is split by the user into systems of one `SystemContainer`, for example
several machines, or variants of one model; each `mbs.SolveDynamic` runs on a thread of its own, and the renderer shows
all systems.

## 1. The starting point: the GIL is never released

`SolveSystem` is bound without `py::call_guard<py::gil_scoped_release>` (`src/Autogenerated/Pybind_modules.h`, the
`SolveSystem` bindings of the solver classes), and the only release of the GIL in the C++ code is in
`MainRenderer::GetGraphicsData` (`src/Main/MainSystemContainer.cpp`). Two Python threads that call `SolveDynamic`
therefore run one after another today; they never race. Parallel solving starts with releasing the GIL in the solve,
and then every place listed below that touches Python must acquire it again.

## 2. Shared state that must become per solver, or be locked

| # | shared state | where | why it matters |
|---|---|---|---|
| 1 | **the task manager** | one global `task_manager` and the statics of `TaskManager` (`num_threads`, `func`, `isRunning`, `jobIsRunning`, `workersSuspended`, `loadBalancing`), `src/Utilities/Threading.h/.cpp` | `CreateJob` is not re-entrant; a second solver takes over or stops the threads of the first (`AcquireWorkers` with `takeOver`) |
| 2 | **`GetNumThreads()` sizes per-system work** | `CSystem.cpp`, `CSystemJacobians.cpp`, `CSystemAssemble.cpp`, `CContact.cpp`, the explicit solvers | one global number decides the parallel paths and the size of the temporary arrays of every system |
| 3 | **thread id 0 means the main thread** | `TaskManager::GetThreadId()`, `thread_local thread_id`; `SymbolicUtilities.h` (`CurrentThreadCopy`) | two solver threads both have id 0 and use the same recording of a symbolic user function, including its `evaluatingItemOutputs` flag |
| 4 | **workers suspended during a factorization** | `LinearSolver.cpp`, `SuspendWorkersDuringFactorization` (#3428) | process-wide: one solver's factorization puts to sleep or wakes the workers of the other |
| 5 | **`pySpecial` counters and flags** | `pardisoFallbacks++` (`LinearSolver.cpp`), `initialConstraintsViolations++` (`CSolverImplicitSecondOrder.cpp`), `multiThreadingLoadBalancing` written by each solver (`CSolverBase.cpp`) | unsynchronized writes |
| 6 | **global timers** | `globalTimers` (`src/Utilities/TimerStructure.h`, `Stdoutput.cpp`), on in release builds, e.g. in `CSystem.cpp`, `CContact.cpp`; reset in Assemble | the counters of two solvers mix, and a reset in one disturbs the other |
| 7 | **a `static` local in `MatrixBase::Invert`** | `src/Linalg/Matrix.cpp`, commented "not THREAD safe" | a data race as soon as two threads invert a matrix |
| 8 | **`pout` and `outputBuffer`** | `Stdoutput.cpp`, `Stdoutput.h` (`suspendWriting`) | one stream: characters of two threads mix before a newline; flushing calls `py::print` (GIL) |
| 9 | **`PyError`, `SysError`, `PyWarning`** | `Stdoutput.cpp`: `PyGetCurrentFileInformation` (Python), `globalPyRuntimeErrorFlag`; `rendererPythonInterface.cpp` | need the GIL; one system's error sets the flag that stops the renderer for all |
| 10 | **Python user functions** | `gil_scoped_acquire` in `SymbolicUtilities.h`, `evaluateUserFunctions.cpp`; `IsExudynMainThread()` (`Symbolic.cpp`) | correct after a release, but they run one at a time; on a solver thread the main-thread checks skip the visualization calls of user items (`CObjectUserBody.cpp`, `CNodeUser.cpp`, `CMarkerBodyUser.cpp`, `CLoad.cpp`) |
| 11 | **the idle operations of the solver loop** | `DoIdleOperations` (`CSolverBase.cpp`): `PyProcessExecuteQueue`, `RendererDoSingleThreadedIdleTasks`, `PyCheckSignals` | global queues taken by whichever solver comes first; GLFW idle tasks belong to the main thread; `PyErr_CheckSignals` needs the GIL |
| 12 | **default file names** | `solution/coordinatesSolution`, `solution/solverInformation.txt` (`SimulationSettings.h`), all under `outputDirectory` | the file handles are per solver, but the default names collide |
| 13 | **the Python layer** | `SolveDynamic` changes the `simulationSettings` it is given and restores it (`python/exudyn/solver.py`) | races if two systems share one settings object |

## 3. Safe as it is

- **The renderer and the systems**: each `CSystem` has its own `postProcessData` with `accessState`, `updateCounter` and
  `SystemAccessGuard` (`CSystem.cpp`, `VisualizationSystem.cpp`, `PostProcessData.cpp`); the renderer locks one system
  at a time.
- **Per-solver data**: `tempCompDataArray` and the solution, sensor and solver file handles.
- **`thread_local` scratch data**: `MarkerData.h`, `CObjectKinematicTree.cpp`, `CObjectUserBody.cpp`,
  `evaluateUserFunctions.cpp`, `Symbolic.cpp`, the user function timer, `pendingExceptionCause`.
- **PARDISO**: loading under a mutex, all calls serialized on one MKL thread (`PardisoMKL.cpp`); correct, but one
  bottleneck for all solvers.
- **Read-mostly globals**: `outputDirectory`, `linalgPrintUsePythonFormat`, `suppressWarnings`, the main thread id.
- No Eigen thread setup and no random generators in `src`.

## 4. Unclear, to check in the design

- `TaskManager::JobIsRunning()` is process-wide, so the guard of `CObjectKinematicTree` can fire on another system's job.
- `MKL_Set_Num_Threads` is process-wide.
- The symbolic statics `SReal::recordExpressions` and `recordingFunction` (`Symbolic.cpp`, `SymbolicTable.cpp`) and the
  non-atomic `userFunctionAssignmentCount`.
- The container flags `updateGraphicsDataNow` and `MainSystemContainer::currentRendererContainer`.
- `PyDeprecated` writes `exudyn.sys`; `warnedComputeEigenValuesANCFcableCircleContact` (`CContactHelpers.h`).

## 5. The hardest obstacles, and what follows for the design

1. **One task manager.** Parallel solvers need either `numberOfThreads = 1` for each system - the systems are the
   parallelism - or a task manager per solver with its own thread count and job state. The first is the natural start:
   the systems run on threads of a pool, each serial inside. `GetNumThreads()` and `GetThreadId()` must then be per
   solver thread (thread-local), not global, and thread id 0 can no longer mean "the main thread" for the symbolic
   recordings.
2. **The GIL.** Released in the solve, it must be acquired again for user functions, errors and warnings, `pout`,
   `PyCheckSignals` and the renderer queues. Python user functions then serialize the systems; symbolic user functions
   do not.
3. **Errors and output are process-wide.** One error flag, one `pout`, one set of queues: a per-solver error state
   and a per-thread output line buffer are needed.
4. **Unsafe globals in the compute path**: the global timers (per solver or off in parallel mode), the static matrix in
   `MatrixBase::Invert`, the `pySpecial` counters (atomic).
5. **Defaults that collide**: a parallel solve should refuse identical output file names and a shared settings object,
   or derive the names per system.

The persistent threads of #3437 (revision2026c step RG5.9.8) are the first piece of the task manager design: they
separate "the threads exist" from "a computation uses them" (`AcquireWorkers`, `ReleaseWorkers` with a ticket).
