(sec-dev-userfunctions)=
# User functions: the C++/Python boundary

How an item stores a user function, how C++ calls a Python and a symbolic one, which thread may call which, and what a
call costs. What a user writes is in {ref}`sec-userfunctions` and on the reference page of each item; the symbolic
side is {doc}`symbolic`.

## 1. The stored function

Every user function parameter of an item is a `PythonUserFunctionBase<UFT>` (src/Pymodules/PythonUserFunctions.h),
`UFT` the `std::function` of its signature; the signatures are instantiated in the generated
`src/Autogenerated/PythonUserFunctionsTemplates.h`. Its base `UserFunctionBase` has what every signature has:

- the kind, `UserFunctionType`: `_None`, `Python`, `Symbolic`;
- the symbolic function, `GetSymbolicFunction()`, for a symbolic function set from Python (`SetPythonUserFunction`
  with an `exudyn.symbolic.UserFunction`); nullptr otherwise;
- `pythonArgument`: an argument of the signature is a Python object (ObjectConnectorUser), so it is never computed
  outside the main thread;
- `ComputableInThreads()` and `PrepareThreads(n)`, for the parallel loops (section 3).

`SetPythonObject` takes a Python function, 0, or the dict `{'function': ..., 'type': ...}` that `GetDictionary` writes,
so a system with symbolic user functions can be copied (#1888). Each assignment raises `UserFunctionAssignmentCount()`.

The generated `GetUserFunctions(ResizableArray<const UserFunctionBase*>&)` of every item lists the user function
parameters of its computation class; itemHeaderEmitter.py writes it from the parameters of type `PyFunction...`.

## 2. The path of one call

Each call of an item goes through a wrapper in src/System/evaluateUserFunctions.cpp inside
`UserFunctionExceptionHandling`, which names the user function in an error; the item number is `GetObjectNumber()`.

**Python** (`EvaluateUserFunction`, `EvaluateUserFunctionIntoVector`, or the `std::function` made by
`PythonUserFunctionToStdFunction`):

- the GIL is acquired; a call from another thread than the main thread is reported (#3003);
- every vector and matrix argument - `StdVector`, an Exudyn vector, a `SlimVector`, the `std::array` of the fixed
  sizes - is a read-only numpy array that views the memory, without a copy (`PythonUserFunctionArgument`,
  `EPyUtils::ToNumpyView`, #3008); `exudyn.special.deprecations.userFunctionListArguments` gives lists instead, one test
  of a bool per argument;
- the result is copied once: a numpy array of the size in one pass (`PythonUserFunctionResult`,
  `EPyUtils::CopyFromPython`), a list item by item; a matrix result into the item's matrix, which keeps its memory
  (#1864).

**Symbolic**: the `std::function` calls the evaluation of the recording ({doc}`symbolic`, section 2), or the items that
take vectors and matrices of run-time size call `EvaluateUserFunctionIntoVector`, `...IntoMatrix`,
`...IntoMatrixContainer` directly, which evaluate into the item's own memory. No vector or matrix is allocated per
call once the sizes are set (#3006, #3021).

**The arguments of an item**: the item passes what it has - its own buffers or views of system vectors - as
`const Vector&`, and the result goes into a `Vector&` or `Matrix&` of the item (`ResizableVector`, `ResizableMatrix`,
which keep their capacity). The fixed sizes (`Vector3D`, `std::array`) need no heap memory.

## 3. Threads

The solver calls the user functions from the main thread, which holds the GIL; the render thread never calls Python
(#3003). With `simulationSettings.parallel.numberOfThreads` > 1, `CSystem::PreComputeItemLists` splits the lists of
the parallel loops - mass matrices, ODE2 residuals, loads, algebraic equations, projected reaction forces - into the
items computed in the threads and those computed in the main thread (#2978):

- an item is computed in the main thread if one of its user functions is not `ComputableInThreads()` - a Python
  function, a symbolic function that cannot be copied, a function with a Python object argument - or if an item
  without user functions in the generated list says `HasUserFunction()`;
- and so is what reads such an item through its access functions: an object on such a node, a marker on such a node
  or object, a connector and a load on such a marker - the same dependencies as for the drawing in the main thread;
- the post-Newton step runs in the main thread if one of its connectors does (#3095).

`CSystem::UpdateUserFunctionsForThreads()`, at the start of each function with a parallel loop, builds the lists again
when a user function was set since they were made - in a preStepUserFunction, say - and prepares the copies of the
symbolic functions of all nodes, objects, markers and loads for the number of threads, once. An item computed in the
threads keeps no buffer that two threads could share: ObjectUserBody and NodeUser keep theirs as `static
thread_local` in the functions that use them.

## 4. The interfaces

`tools/benchmarks/userFunctionInterfaces.py` reads the signatures from the definitions (`--all` lists every user
function); the classes say what crosses the boundary beyond `mbs`, `t` and the item number. As of 1.13.203:

| signature class | user functions | with a symbolic version | distinct signatures |
|---|---:|---:|---:|
| run-time vectors in, matrix out | 17 | 17 | 7 |
| run-time vectors | 15 | 13 | 11 |
| scalars | 12 | 12 | 6 |
| fixed-size vectors and matrices | 8 | 8 | 5 |
| graphics | 5 | 0 | 2 |
| **all** | 57 | 50 | 31 |

Without a symbolic version: the five `graphicsDataUserFunction`s, whose result is a Python dict of graphics data,
`ObjectConnectorUser.forceUserFunction`, which gets Python objects of its markers, and
`SensorUserFunction.sensorUserFunction`, which reads through `mbs`. A symbolic function is recorded with the real
`mbs`: what it reads from there is a constant (#2984).

## 5. The cost of a call

Measured with `tools/benchmarks/userFunctionPerformance.py` on the runs of
`python/PerformanceModels/perfUserFunctions.py` (also part of the performance suite): one representative per class,
explicit RK44, microseconds per call = (solver time - solver time of the model without the user function) / calls,
fastest of 5, Windows, Python 3.13, 1.13.141 (the column without a version). 1.13.6, a copy of its installed package, is the reference every change
of the user functions is measured against (maintainer 2026-10-16: the performance shall improve, or at least not drop).

| function | class | Python 1.13.6 | Python | symbolic 1.13.6 | symbolic | Python/symbolic |
|---|---|---:|---:|---:|---:|---:|
| spring (CoordinateSpringDamper) | scalars | 0.348 | 0.367 | 0.069 | 0.077 | 4.8 |
| preStep (MainSystem, once per step) | scalars | 0.191 | 0.213 | 0.018 | 0.013 | 16 |
| load (LoadForceVector) | fixed size | 1.357 | 1.244 | 0.097 | 0.062 | 20 |
| cartesian (CartesianSpringDamper) | fixed size | 3.643 | 2.836 | 0.285 | 0.230 | 12 |
| rigid6 (RigidBodySpringDamper, 6D) | fixed size | 7.076 | 4.755 | 0.437 | 0.407 | 12 |
| generic6 (GenericODE2 force) | run-time vectors | 2.948 | 2.041 | 0.403 | 0.080 | 26 |
| generic10 | run-time vectors | 3.284 | 2.052 | crashed (#2998) | 0.083 | 25 |
| generic100 | run-time vectors | 10.105 | 2.051 | crashed (#2998) | 0.257 | 8 |
| ode1x6 (GenericODE1 rhs) | run-time vectors | 1.547 | 0.977 | 0.239 | 0.022 | 44 |
| mass6 (GenericODE2 mass matrix) | matrix out | 4.339 | 3.406 | crashed | 0.373 | 9 |

- **Symbolic**: what remains is the arithmetic and what is copied. `rigid6` copies two 6 x 6 and two 3 x 3 matrices
  into the named matrices per call (#3039); `mass6` builds 36 expressions, 30 of them constant zeros.
- **Python**: the call costs about 0.2 us, the rest is the numpy work of the body; the arguments as numpy views make
  a function of 100 coordinates cost what one of 6 costs.
- `tools/benchmarks/userFunctionBoundary.py` measures one call with vectors of 1 to 1000 items;
  `tools/benchmarks/measureUserFunctions.py` the cost of a call into Python against C++ in a chain of mass points.

## 6. Decisions

| decision | why |
|---|---|
| the arguments of a Python function are read-only numpy views, valid during the call (maintainer 2026-10-16, #3008) | no O(n) conversion, `K @ q` works; a function that keeps `q` copies it |
| `userFunctionListArguments` for the transition, until 2031 | it costs one test of a bool per argument |
| an item passes `const Vector&` and receives into `Vector&`; symbolic functions evaluate into the item's memory (#3005, #3006) | no allocation per call in either kind |
| one wrapper per user function in evaluateUserFunctions.cpp | pybind11 and MainSystem.h stay out of the item sources |
| the main thread for Python, the threads for symbolic functions that can be copied (#2978) | the GIL; one recording serves many items |
| the lists follow a user function set during a simulation (#2978) | an item that gets a Python function in a preStepUserFunction must not be computed in a thread |
