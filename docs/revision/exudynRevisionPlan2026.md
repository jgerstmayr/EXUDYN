context in a Claude Code session: it carries the measured facts, the decisions already taken
and their reasons, and the step list.

- **Analysis date**: 2026-09
- **Scope**: 79 steps, 10 phases (steps 64–79 added 2026-09, see §5). Performance tuning is explicitly *out of scope*
  (deferred to a later phase); the two exceptions are the alignment fix (step 22) and the

### Branches

| branch | purpose | pushed to |
|---|---|---|
| `master` | mirrors public GitHub `master`; stays at 1.11.0 | GitHub, only at v2.0 release (step 12) |

### Remotes

```
origin  →  git@<internal-gitlab>:<group>/exudyn.git      internal   (v2-dev tracks origin/v2-dev)
github  →  git@github.com:jgerstmayr/EXUDYN.git        public     (master tracks github/master)
```

`origin` is the internal server, so a bare `git push` from `v2-dev` goes there — the safe default.
`master` still tracks `github/master`, which is correct: it exists to mirror public state, not to
be developed on.

### The rules

- **Work on `v2-dev`. Never commit on `master`.** `master` is a read-only mirror of public state.
- Push `v2-dev` to `origin` freely; that is the point of having it.
- Nothing reaches GitHub before the v2.0 release (D6). `tools/hooks/pre-push` enforces this
  mechanically — see step 9 — but it only works where `core.hooksPath` is set, which is per clone.
- Claude never pushes to any remote under any circumstances, and announces any network access
  before it happens (GitHub 2FA is released by hand and otherwise times out silently).

### Seeding another clone or another server

The internal server holds full history, so an ordinary `git clone` of it gives a complete
repository. To seed a *new* empty server from a shallow clone, see step 5: push the full history
first from a full clone, in chunks under GitLab's 1.17 GiB pack limit, then push `v2-dev`.

## 3. Verified facts (do not re-litigate)

These were checked against the tree. Several correct earlier assumptions.

1. **`main/obj/cppsrc.vcxproj` is live and current**, not stale. 133 `ClCompile` entries;
   `setup.py` lists exactly 133 `.cpp` files; it contains every recent addition
   (`Symbolic.cpp`, `Raytracing.cpp`, `CObjectANCFThinPlate.cpp`, `GlfwClientExtended.cpp`,
   `Threading.cpp`). It is the de-facto source list and the primary development environment.
2. **The dead build files** are `main/CMakeLists.txt`, `main/src/CMakeLists.txt`
   (2019-era subset, hard-coded `python38` include path) and `main/obj/autoCMakeLists.txt`.
3. **MSVC cannot load a project from `pyproject.toml`.** No PEP 517 project system exists.
   The only sln-free route is CMake folder mode, which trades the `.pyproj` mixed-mode
   debugging checkbox for an attach-to-process step. Decision: keep `.sln` + `.vcxproj`.
4. **`__FAST_EXUDYN_LINALG` is ABI-safe.** Every occurrence is macro-only — range checks in
   `ReleaseAssert.h`, timers in `TimerStructure.h`, verbosity in `CSolver.h`. No conditional
   members, no struct layout change.
5. **`use_AVX2` is *not* ABI-safe**: it changes `exuMemoryAlignment` (1 → 4 for double) and
   `exuVectorLengthAlignment` in `BasicDefinitions.h:125-148`. Default and fast variants are
   therefore not interchangeable for compiled plugins.
6. **The AVX2 speedup comes from the optimiser**, auto-vectorising the fixed-size
   `ConstSizeVector` / `ConstSizeMatrix` templates at their inline call sites — not from the
   intrinsics in `Linalg/Use_avx.h`. It cannot be isolated into dispatched kernels, and the
   variants must stay whole separate modules (see §5, step 23).
7. **Linux has never had AVX2**: `useAVX` is Windows-only in `setup.py`, so `__AVX2__` is
   never defined and `-O3` auto-vectorises only to 128-bit SSE2. Root cause is the alignment
   bug in step 22, not a compiler limitation.
8. **The object factory is already a runtime registry.**
   `ClassFactoryItemsSystemData<MainObject>::Get().RegisterClass(name, lambda)` in
   `Autogenerated/objectFactoryAutoReg.h`; `MainObjectFactory::AddMainObject` dispatches
   purely on the `objectType` **string** from the Python dict. No `py::class_` is needed for a
   user object. The single blocker for plugins is the function-local static in
   `MainObjectFactory.h:97`, which gives every binary its own private map.
9. **`mainSystemExtensionsHeader.py` is copied verbatim** into
   `pythonDev/exudyn/mainSystemExtensions.py`; the generator's only transformation is
   appending 128 lines of `exu.MainSystem.X = Y`.
10. **The `#**` doc-comment parser accepts exactly 11 tags** (`utilitiesDocuGenerator.py:116`)
    and silently drops everything else. The sources contain `#**note:` (9×), `#**nodes:` (3×),
    `#**examples:` and `#**outputinput:` — 14 pieces of written documentation that reach
    nothing.
11. **Generators mostly skip unchanged files — but not all of them.** `WriteTextIfDifferent(file,
    text, ignoreDateStrings)` in `autoGenerateHelper.py:181` compares content while ignoring
    `* @date` and `// AUTO:  last modified` lines, and `pythonAutoGenerateObjects.py` /
    `pythonAutoGenerateSystemStructures.py` both report "files changed = 0" on a no-op run.
    `autoGeneratePyBindings.py` used to be the exception — it rewrote
    `main/src/Autogenerated/pybind_manual_classes.h` unconditionally, so the `// AUTO:  last
    modified` line changed on every run. **Fixed 2026-09-09**: that write now goes through
    `WriteTextIfDifferent(..., ignoreDateStrings=True)` like the others, verified by two
    consecutive runs producing no diff.

    **But `git status` alone is still not a sufficient drift signal** (measured while building
    step 2's tool). Every generated file carries a `@date ... (last modified)` line. Once a file is
    rewritten for any reason — a temporary input change, an interrupted run — that line differs
    from HEAD and *never reverts*, because `WriteTextIfDifferent` then considers the content equal
    and declines to write again. `git status` reports that file as modified forever, while the
    content is identical. A gate built on `git status` alone would therefore emit phantom failures
    and be trained away. `tools/regenerate.py` reuses `IsEqualIgnoringDateStrings` from
    `autoGenerateHelper.py` to compare each flagged file against HEAD, exactly as §4.4 prescribes.
12. **History claim retracted**: earlier remarks about squashed release drops were inferred
    from a depth-1 clone (`.git/shallow` present, `rev-list --count` = 1). GitHub history is
    release-granular per the maintainer's description, not per measurement.

17. **RESOLVED 2026-09-09 (step 71).** `pythonAutoGenerateSystemStructures.py:1357` emitted four

18. **Multi-platform text handling is a standing concern, not a one-off.** Everything to date has
    been generated and built on Windows, so encoding and line-ending defaults have never been
    exercised elsewhere. Step 71 fixed the encoding defaults; step 70 (`.gitattributes`) covers
    line endings. Any *new* file IO in the generators or tools must pass `encoding='utf8'`
    explicitly — never rely on the platform default. Worth a lint rule when step 43 adds ruff
    (`PLW1514` / `flake8-encodings`).
19a. **The scipy slowdown localised to one test (2026-09-10).** On the GitLab runner with an
    unpinned scipy, `abaqusImportTest.py` alone took **60.0 s of the 106 s** suite — 56% of the
    whole run for one otherwise unremarkable test, against 1.1 s for the comparable
    `compareAbaqusAnsysRotorEigenfrequencies.py`. Consistent with fact 19: it is the sparse
    eigenvalue solver. `tools/ci/buildManylinux.sh` now pins `scipy==1.15.2`; raise that pin
    deliberately and re-measure. This is also a **user-facing** performance regression, not only a
    CI annoyance — anyone on current scipy pays it in their own eigenvalue work.

19. **scipy 1.18.0 causes a large test suite slowdown** — attributed to the eigensolver path.
    Measured on the same machine and the same Exudyn 1.11.0: `venvP312` (scipy 1.15.2 /
    numpy 2.2.4) runs the suite in **24.3 s**, `venvExuP313` with scipy 1.18.0 / numpy 2.5.2 took
    **more than 10 minutes**; downgrading that environment to scipy 1.15.2 (numpy 2.4.6) brought it
    back to **22.5 s**. NGsolve's presence makes no difference. Two consequences: the ~20 s figure
    that makes gate 3 cheap is **not** a property of the suite alone, and users on current scipy may
    be silently paying the same cost in their own eigenvalue work. Worth isolating to a specific
    scipy call and reporting upstream if it reproduces standalone; until then, pin scipy in the
    reference environment and record the scipy/numpy versions alongside the timing in
    `TestSuiteLogs/`.

20. **The 5e-14 test tolerance is too tight to be environment-independent.** In the scipy 1.15.2 /
    numpy 2.4.6 / Python 3.13.15 run, `movingGroundRobotTest.py` fails at
    `ERROR = 5.0688e-14` against `tol = 5e-14` — 1.4 % over the wall, with result and reference
    agreeing to about 13 significant digits (`0.007681798995995473` vs `0.007681798995944785`).
    That is last-bits floating-point noise from a different BLAS/library build, not a regression.
    The same suite passes 106/106 under numpy 2.2.4 / Python 3.13.2. The error distribution shows
    the next-largest at 3.33e-14, so at least two models sit close to the limit.

    **Worked around 2026-09-09**, not fixed: the test's output scaling factor was halved
    (`fact=0.01` → `0.005` in `movingGroundRobotTest.py`), with the reference value in
    `runTestSuiteRefSol.py` updated to match (`0.0038408994979977364`). Because the suite compares
    with a single *absolute* tolerance, scaling the reported quantity down scales its absolute
    error down with it, giving roughly 2× headroom. The suite passes again.

    The general problem stands: one global 5e-14 absolute tolerance means a model's margin depends
    on the magnitude of whatever it happens to report, so headroom is bought by rescaling rather
    than by stating what accuracy the model actually needs. This is concrete justification for
    step 40's **per-model tolerances** — a flaky gate gets ignored. Until then, a near-tolerance
    failure should be checked against this fact, comparing the reported `RESULT` against `refsol`,
    before being treated as a real break.


21. **Regeneration must run *after* `ResolveIssue`, not before.** `ResolveIssue` rewrites
    `docs/theDoc/version.txt`, and `README.rst` plus `docs/RST/Exudyn.rst` embed the version string
    (`Exudyn version = 1.11.4 (McLaughlin)`), refreshed only by `doc2rst.py`. Regenerating first
    therefore leaves those two files one version behind and makes the next drift check report a
    change unrelated to the work. This constrains step 2: `tools/regenerate.py` cannot be run as a
    pre-commit hook independent of the tracker — either it runs after the version bump, or the
    check must know that these two files legitimately trail. Simplest is to keep the ordering
    explicit in the gate, which `docs/dev/WORKFLOW.md` now does.

22. **Long file names broke checkout on Windows** (found 2026-09-09 while testing the shallow
    push). Several marker files carried their note *as the file name*, up to 140 characters —
    `main/src/Solver/#linear solver - nonlinear solver - ... .txt` and five siblings. Cloning into
    a moderately deep directory exceeded the Windows 260-character `MAX_PATH` and failed with
    `Filename too long`, leaving **a broken checkout**, not merely a warning. Invisible to anyone
    working from a short path such as `C:\DATA\cpp\`. Resolved by shortening or removing them; the
    longest tracked path is now 118 characters, leaving 142 for the clone directory. Keep it that
    way: a new path over roughly 150 characters is a portability bug for users, not a style matter.

23. **CI could not fail, and had not been able to for as long as it existed** (found 2026-09-09
    while building step 11). Two independent causes: `.github/workflows/wheels.yml:18` sets
    `continue-on-error: true`, and `runTestSuite.py` contained no `sys.exit()` — it returned 0 even
    when tests failed. The failure count reached a human only through the *log file name*
    (`...-F<NN>`, `-F00` = clean). So a red suite produced a green workflow.

    **Fixed 2026-09-09**: `runTestSuite.py --exit-code` returns non-zero on failure, and the
    `-F<NN>` suffix is gone — the exit code carries that information, and the varying name meant
    each differing failure count left a *new* log file instead of replacing the previous one,
    slowly filling `TestSuiteLogs/`. The GitLab jobs set no `allow_failure`. Whenever GitHub CI
    resumes, `continue-on-error: true` should go with it (see step 20).

24. **Test reproducibility is not uniform, and one global tolerance cannot express that.** Contact
    and friction models are chaotic, and sparse eigenvalue problems go through ARPACK from a random
    start vector with no seeding hook. Both give materially different errors on different machines,
    so the magnitude of the error carries no information about correctness. This is the root cause
    of the `movingGroundRobotTest` failure in fact 20.

    `runTestSuiteRefSol.py` now carries two data tables: `TestExamplesToleranceFactors()` (a
    per-test multiplier on the global tolerance — this concept already existed, hard-coded inline
    in `runTestSuite.py`, with a comment naming the sparse eigenvalue solver) and
    `SensitiveTests()`, whose members are run and reported but **excluded from the exit code**.

    `SensitiveTests()` is deliberately **empty**: it must be filled from cross-platform evidence,
    not guessed. A file-name match on contact/friction/eigen hits 37 of the 106 tests and would
    remove a third of the suite from the gate for no reason — most eigenvalue tests are dense and
    deterministic. Fill it by comparing per-test `ERROR` values across Windows, Linux and macOS.

25. **`main/src/Main/Experimental.h` is a feature-flag mechanism, not stray debug code.**
    `class PyExperimental`, exposed to Python via `PybindModule.cpp`, exists so a method can *ship
    behind a switch* while incomplete — needed for a paper, or waiting on a "part B". Flags default
    to off, so a release carries the code without advertising it, and a small group can enable it.

    Recorded because the step 8 name-based scan flagged it as experimental leftover and proposed
    raising an issue to remove it. That would have deleted a deliberate mechanism and changed the
    public Python API. **A name scan finds candidates, not conclusions** — every hit needs a human
    read before action. Described in `docs/dev/ARCHITECTURE.md` so it is discoverable rather than
    folklore.

26. **There are two build modes, switched by one line in `issueTracker.py`.** `versionDev` at
    `issueTracker.py:56-57` selects:

    | mode | `versionDev` | version string | modules built |
    |---|---|---|---|
    | **release** | `''` | `1.11.14` | all — `exudynCPP` **plus** `exudynCPPfast`, plus `exudynCPPnoAVX` on Windows |
    | **development** | `'.dev1'` | `1.11.14.dev1` | one `exudynCPP`, **except** the Python versions used to measure the fast-variant speedup |

    `setup.py` reads the version string and gates on it: `compileExudynFast` builds for all Python
    versions on a release but only for Python 3.10 on a `.dev1` version, and `exudynCPPnoAVX`
    likewise. The effect is large — measured on Windows/cp313, **168.9 s release against 58.1 s
    development** (step 4).

    The `.dev1` suffix also changes what pip does: such a version is not installed by a plain
    `pip install exudyn`, only with `--pre` or an exact version, so a development build cannot
    reach users by accident.

    **Both modes are intended and must be kept.** Switching is currently a hand edit followed by
    `UpdateFiles()`; step 65 should make it a command (`--release` / `--dev`), and a small Tkinter
    front-end is wanted later. Two consequences worth remembering: a mode switch changes the
    version string, so it propagates into `README.rst` and `docs/RST/Exudyn.rst` on the next
    regeneration (fact 21); and any build-time comparison is meaningless unless both sides are in
    the same mode.

### 3a. Python environments (measured)

`python` is not on `PATH`. **`venvExuP313`** (created 2026-09-09) is the reference environment and
covers generators, the sphinx docs build and the test suite in one place; `venvP310`–`venvP314`
carry per-version Exudyn builds for the test matrix. The recipe and the package-to-feature mapping
are in `docs/howTo/condaEnvironments.md`, which is one of the `howTo` files that survives step 30.

The base Anaconda environment carries a stale **exudyn 1.10.0**, so a test run from it silently
tests old binaries. Always check `exudyn.__version__` against `docs/theDoc/version.txt`.

**Dependency policy**: numpy is the only hard requirement — it follows from the nature of the
C++/Python coupling. Advanced functionality (scipy, networkx, Gym, stable-baselines, NGsolve, …)
stays **optional**: installation requires the minimum, and a function needing more raises at the
point of use. Today those failures are not consistently `ImportError`; making them a single
recognisable, actionable exception type belongs to Phase 5 (steps 46–49).

## 4. Phase 0 — the frozen generated set

The committed generated files at `e44aca1` are the reference snapshot, after a rebuild
confirms they are current. This section defines what `tools/regenerate.py` compares.

### 4.1 Comparison procedure

Because of fact 11, no temp-directory diffing is needed:

```bash
# 1. clean tree, everything committed
git status --porcelain            # must be empty

# 2. run every generator from its required cwd
cd main/src/pythonGenerator
python pythonAutoGenerateObjects.py
python pythonAutoGenerateSystemStructures.py
python autoGeneratePyBindings.py
python utilitiesDocuGenerator.py
python createStubFiles.py
python doc2rst.py
# NOT makeAllBinariesScripts.py — it only writes the volatile build date

# 3. drift check
git status --porcelain -- <TIER 1 PATHS>     # must be empty → hard gate
git status --porcelain -- <TIER 2 PATHS>     # should be empty → warn
```

**Establish the manifest empirically before trusting the lists below.** Run the generators
twice on an unmodified tree. Anything that changes on the *second*, no-op run is volatile and
must be excluded or normalised. The lists below are the starting point from a static reading
of the generator write targets, not a substitute for that experiment.

### Phase 8 — Compiled user extensions (after Phase 5)

Additive; nothing earlier changes. Two shipped variants remain after step 23, so a plugin is

**Founding policy**: a plugin author builds exudyn from source once, then builds the plugin with
the same toolchain. Compiler, CRT and flags are then identical by construction, so no C-ABI shim
is needed — plugins inherit from `CObject` directly.

55. Make the registry cross-binary. `MainObjectFactory.h:97` holds its singleton in a

    path needs no change.
56. Define an ABI fingerprint checked at registration: exudyn version, active macro set, compiler
    id and version, `__cplusplus`, and on MSVC `_ITERATOR_DEBUG_LEVEL` plus the CRT model. Add

    a plugin author will do.

## 8. Failure modes to watch for

Cheap to state, expensive to discover late.

1. **Partial ISA duplication** (step 23) — compiling only some translation units with AVX2 lets
   the linker keep one copy of an inline template instantiation, which then executes AVX2 code on
   a baseline CPU. All-or-nothing per link unit.
2. **Moving and editing files in the same commit** (step 25) — destroys rename detection.
3. **Adding plugin discovery before step 47** — every plugin failure becomes indistinguishable
   from a binary-selection failure.
4. **Debug plugin against Release core** (step 56) — crashes inside `std::map` with no useful
   stack.
5. **Silent generator drift** — the reason step 2 comes first.
6. **The wheels matrix during the freeze** — 20 build configurations breaking invisibly.

## 11. Session workflow

A Claude Code session's working contract is `CLAUDE.md` in the repository root; the operational
detail is `docs/dev/WORKFLOW.md`. In short:

1. Work one step at a time and cite it by number.
2. Every non-trivial change is an issue in `tools/issueTracker/trackerlog.txt`, raised through
   `issueTracker.py` — never by hand-editing the file.
3. Before a normal commit: the build succeeds, regeneration produces no drift, the **full**
   `runTestSuite.py` passes (~20 s — never a subset), and docs plus this plan are updated.
4. `ResolveIssue()` closes the issue and bumps the micro version, rewriting seven files. Then a
