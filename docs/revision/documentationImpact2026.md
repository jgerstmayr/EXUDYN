# What this revision changes for the documentation

*Revision2026 step R7.2.2. Written 2026-09-21; the work list of step R7.2.3 and the material of
R7.2.4.*

The plan and the log are records of **decisions and work**. This file is the third thing: the list
of what a **reader of the documentation** runs into because of them — a name that no longer exists,
a command that was replaced, a feature that nothing describes yet. One row per item, with where it
stands today and what has to happen.

It is a working document like the plan, not a published page (`docs/revision/*` is excluded from
the Sphinx build). It is written down rather than held in a session because it outlives the
session, and because the next revision will want the same list again.

**How the lists below were produced** — three scans over the tree, not from memory:

1. every name this revision removed, moved or renamed, searched in the hand-written pages
   (`README.rst`, `index.md`, `CONTRIBUTING.md`, `docs/manual/`, `docs/dev/`, `docs/howTo/`);
2. the same search over the emitted pages, to tell a wrong *page* from a wrong *source*;
3. the leftovers of the LaTeX-to-Markdown conversion of R7.1 (`{\"o}`, RST directives, escapes
   that mean nothing in Markdown).

`CHANGELOG.md` and `docs/generated/trackerlog.md` are **excluded from all three**: they are
records of issues, and an issue from 2023 that speaks of `theDoc.tex` is correct as it stands.

## D. What goes into the revisions chapter (R7.2.4)

The chapter is short and is written for a **user upgrading from 1.11**, in this order:

1. **what breaks**: the star-import change, removed and renamed names (info §14), and the checker
   of revision2026b step RG10.1 that finds them in a script;
2. **what is new to use**: `python -m exudyn`, the environment variables that keep a run silent,
   the exception types, the fast module;
3. **what is new to read**: the documentation is Markdown and is published for every release;
   `CHANGELOG.md`; the issue tracker page;
4. **what changed in how the project is built and released**, in two sentences, because a user of a
   wheel does not need more: CI builds the wheels, `exudev` drives everything else.

It is structured **by release** (2.0 first, later ones above it), not by plan phase, so that the
next revision appends a section instead of rewriting the chapter. The plan, the log and this file
stay out of the published documentation.

## E. Deliberately not in the documentation

- the plan (`exudynRevisionPlan2026.md`), the log and this file — records of how the work went,
  not statements about the product;
- step numbers (`R8.3.4`): they are permanent for *this* project's record, and mean nothing to a
  reader. The revisions chapter names features, not steps;
- issue numbers in prose, except where the tracker page and the changelog already carry them.
