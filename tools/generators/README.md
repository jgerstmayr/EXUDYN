# tools/generators/ — the new generator code

Maintainer tools around [`definitions/`](../../definitions/README.md), the input of code
generation. The six established generators still live in `src/pythonGenerator/`; the code here
grows as Phase 3 splits them into emitters (revision plan step 33).

| file | what it does | used by |
|---|---|---|
| `definitionLoader.py` | imports `definitions/` and hands each class to the generators as `(parseInfo, parameterList)` - the form their old line parser produced - so their per-class code is unchanged. Removed once the generators read `definitions/` directly (step 33, part 2) | `src/pythonGenerator/pythonAutoGenerateObjects.py`, `pythonAutoGenerateSystemStructures.py` |
| `itemModel.py` | facts about items shared by the emitters: type tables and predicates, user-function types, how a `definitions/` member renders to the old string forms, per-item accessors | the emitters, `definitionLoader.py`, `pythonAutoGenerateObjects.py` |
| `itemInterfaceEmitter.py` | emits `python/exudyn/itemInterface.py` from `definitions/`; `--output` for another target | `tools/regenerate.py` |
| `definitionValidator.py` | the cross-file checks on `definitions/`: every virtual item function overrides a real declaration in the C++ parent headers, `fromParent` members exist in the parent, no duplicate member, shaped defaults have the right size; reports all violations | `tools/regenerate.py`, before the generators run (exit code 3) |
| `outputVariableEmitter.py` | generates `src/Autogenerated/OutputVariableTypes.h` from `definitions/outputVariableTypes.py`, after checking the bit allocation | `src/pythonGenerator/autoGeneratePyBindings.py`, on every generation |

## Changing a definition

Edit `definitions/`, then in `venvExuP313`:

```
python tools/regenerate.py --check
```

It validates the definitions, runs all generators and reports what changed in the generated set.
